# Data Ownership / Resource Boundary (IS-004)

**Класс:** B — Platform Service
**Уровень:** Level 0 — Modular Monolith
**Версия компонента:** 0.1.0
**Владелец данных:** `records` (логическая схема `records`)
**Задача:** Issue #14
**Архитектурная основа:** `docs/ARCHITECTURE.md` v1.2.0 §5.3, §5.4, §6.1, §6.2,
§26, §27, LAW-03, LAW-04, LAW-16, LAW-16a

IS-004 — компонент-владелец данных. Он доказывает, что означает `ALLOW` от
IS-003 на границе, которая владеет данными: **`ALLOW` не является прямым
доступом к данным — владелец данных остаётся финальной границей контроля**
(§6.2). Авторизованный запрос может работать только с ресурсом, которым
владеет этот компонент, и не может обойти границу авторизации IS-003.

Это не ORM, не data platform и не универсальный сервис доступа к данным:
компонент владеет ровно одним набором доказательных ресурсов и ровно одной
границей контроля.

## Цепочка, которая доказывается

```text
Identity A (IS-001)
      ↓  эффективный тенант — только из IS-001
Authorization Boundary (IS-003)
      ↓  ALLOW — данные, а не доступ
Resource Boundary (этот компонент)
   ├─ ресурс существует у этого владельца?        иначе DENY
   ├─ единственный владелец ресурса — записан?    иначе DENY
   ├─ решение власти получено и авторитетно?      иначе DENY (закрыто)
   └─ решение власти — ALLOW + permitted?         иначе DENY
      ↓
owned-data операция выполняется только здесь, в конце цепочки
```

Порядок шагов опубликован (`api.enforcement_model.enforcement_chain`) и
является частью поведения: каждый шаг может только отказать, и ни один отказ
не превращается в доступ. Операция над данными (`serve_resource` /
`apply_transition`) вызывается ровно один раз и только после полного
прохождения цепочки — тесты считают именно эти вызовы, чтобы доказать, что
отклонённый запрос до них не доходит.

## Минимальная модель ресурса

| Поле | Смысл |
|---|---|
| `resource_id` | идентификатор ресурса |
| `resource_type` | `record` — единственный тип этого среза |
| `owner_component` | ровно один владелец; факт регистрации, не запроса |
| `tenant_id` | Tenant, которому принадлежит ресурс, — факт хранилища владельца |
| `state` | `draft → active → archived` (переходы `activate`, `archive`) |

## Инварианты

| № | Инвариант |
|---|---|
| R-001 | У каждого ресурса ровно один владелец данных |
| R-002 | Субъект Tenant A не получает ресурс Tenant B — ни сменой `resource_id`, ни caller-supplied `tenant_id` |
| R-003 | Запрос с `DENY` от IS-003 не доходит до операции над данными |
| R-004 | Отказ или нечитаемый/неавторитетный ответ зависимости авторизации закрывается в `DENY` |
| R-005 | Эффективный тенант — только из IS-001; второго tenant-context механизма здесь нет |
| R-006 | Публичная поверхность не содержит пути доступа в обход границы владельца |
| R-007 | Security-значимые отказы аудируемы и наблюдаемы с `request_id` / `correlation_id` и actor/tenant контекстом, где он известен |
| R-008 | Внутренности компонента не являются потребительским контрактом |

## Публичный контракт

- HTTP: `GET /api/v1/resources/{resource_id}` (операция `records.read`) и
  `POST /api/v1/resources/{resource_id}/transitions` (операция
  `records.write`) — см. `contract/openapi.yaml` и
  `contract/component_contract.json`;
- уровень 0 (in-process): `records_service.reader.RecordsClient` — ровно две
  операции, значения туда и обратно.

`Authorization` несёт credential субъекта: компонент сам не проверяет
никаких credentials — предъявленный credential проверяется в IS-001 внутри
решения IS-003. `X-Tenant-Id` — только cross-check: он передаётся в решение
как есть и никогда не выбирает эффективный тенант (LAW-16a).

Граница контрактно-опосредованная: клиент выполняет опубликованный
HTTP-контракт внутри процесса через `records_service.transport`
(`open_channel` регистрирует приложение компонента и отдаёт непрозрачный
дескриптор канала, `call_contract` выполняет по нему запрос). Состояние
клиента — одно значение (дескриптор канала), среди значений нет вызываемых
объектов. Поэтому через опубликованную поверхность недоступны хранилище
ресурсов, журнал аудита, engine и операции регистрации ресурсов — ни под
открытым именем, ни под закрытым, ни через `__closure__`. Дескриптор
отзывается, когда потребитель выпускает клиента; неизвестный или отозванный
дескриптор означает отказ (`ContractViolation`), а не разрешение.

Опубликованная поверхность **не содержит** операций перечисления, массового
чтения, экспорта или прямого доступа к хранилищу: два опубликованных пути —
единственные, и оба проходят цепочку контроля. Обходить нечего: другого пути
не существует (R-006).

## Отказы

| Статус | Причины |
|---|---|
| `401` | `missing_identity`, `invalid_identity`, `unknown_identity` |
| `403` | опубликованные `DENY`-причины IS-003 без изменений; `owner_mismatch` |
| `404` | `resource_unknown` — решение у власти не запрашивается |
| `409` | `invalid_transition` — доменный отказ после ALLOW |
| `422` | `malformed_request` — запрос нечитаем опубликованной схемой |
| `503` | `authorization_unavailable` — зависимость не ответила или ответила вне контракта |

Ответ вне контракта (не-JSON, отсутствие ответа, неизвестная причина)
поднимает `records_service.errors.ContractViolation` — потребитель падает
закрытым, а не считает ресурс выданным.

`DENY`-причины власти проходят сквозь границу без изменений: факт
принадлежит IS-003. Собственные причины компонента — только три плюс
доменный отказ. Неавторитетный ответ — в том числе `ALLOW` с причиной,
отличной от `permitted`, или `DENY` с неизвестной причиной, — закрывается
как `authorization_unavailable`: указание направления не делает ответ
авторитетным (R-004).

## Зависимость от IS-003

| Компонент | Механизм | Операции |
|---|---|---|
| IS-003 `authorization` (`>=0.1.0,<0.2.0`) | клиент над опубликованным API | `decide` |

Зависимость — на контракт, а не на код: **ни один модуль `records_service`
не импортирует `authorization_service`, `identity_service` или
`tenant_authority`**. Между опубликованным клиентом и логикой контроля стоят
три собственные вещи компонента:

| Слой | Модуль | Роль |
|---|---|---|
| порты | `records_service.ports` | что компоненту нужно: одно решение, описанное только его собственными типами |
| значения | `records_service.consumed` | `DecisionAnswer`, `DependencyRefusal` — во что превращается чужой ответ |
| адаптеры | `records_service.adapters` | единственное место, знающее форму опубликованного ответа IS-003 |

Адаптер читает из ответа только то, что документировано контрактом, и сразу
превращает его в значение этого компонента: ни один объект провайдера не
переживает вызов адаптера и не попадает ни в движок, ни в выданный ресурс,
ни в журнал аудита. Вопрос о ресурсе формулируется с `resource_tenant_id`
из собственного хранилища владельца — никогда из заявления вызывающей
стороны.

Собственного вывода тенанта и собственной проверки прав в компоненте нет:
если порт не отвечает, компонент не может выдать ничего — даже «свои»
ресурсы. Это и есть доказательство отсутствия второго механизма
авторизации/тенант-контекста (R-005). Компонент не собирает платформу:
клиент IS-003 передаётся извне композиционным корнем, поэтому модульного
демо-приложения у компонента нет — демонстрация владельца данных требует
собранной Platform Instance.

## Данные компонента

| Набор | Область | Комментарий |
|---|---|---|
| `resources` | `tenant-scoped` | ровно один владелец на ресурс; регистрация явная и не переопределяется |
| `access_audit` | `platform-scoped` | append-only журнал каждой попытки доступа — разрешённой и отклонённой |

Компонент не владеет идентичностями, грантами, реестром тенантов и
состояниями тенантов — это данные `identity`, `authorization` и
`tenant_authority`, читаемые через их опубликованные контракты.

## Аудит и наблюдаемость

Каждая попытка доступа записывается с `action` (`records.read` /
`records.write`), `decision`, `reason`, `subject_id`, `tenant_id`,
`resource_id`, `resource_tenant_id` (факт хранилища), `claimed_tenant_id`
(заявление вызывающей стороны — отдельно), `platform_id`, `request_id`,
`correlation_id`, `timestamp`. Отказ, произведённый схемой до обработчика
(`malformed_request`), также аудируется: фиксируется расположение и вид
проблемы, но не присланные значения. Журнал — внутренние данные компонента:
через опубликованную поверхность он не читается.
