# Operating Model

**Статус:** `PROPOSED` — ожидает архитектурного ревью и ратификации
**Версия:** 1.0.0
**Дата:** 2026-09-08
**Уровень изменения:** Level A — операционная процедура (ADR не требуется, см. §34.1 ARCHITECTURE.md)
**Основание:** Issue #4 (DOC-001)

---

## 1. Назначение

Этот документ определяет операционную модель разработки `application-factory`
через скоординированную работу ChatGPT и Arena с GitHub как единственным
источником истины.

Этот документ:
- **не заменяет** `docs/ARCHITECTURE.md`;
- **не определяет** архитектуру системы;
- **не создаёт** архитектурных законов;
- **не изменяет** LAW-01…LAW-16 и не создаёт новых.

Операционная модель описывает **как** команда работает, а не **что** строится.

---

## 2. Единый источник истины

GitHub является единственным источником истины проектной работы.

Информация считается частью проекта только тогда, когда она зафиксирована
в репозитории или в рабочих артефактах GitHub.

Ролевое назначение артефактов GitHub:

| Артефакт | Назначение |
|---|---|
| `docs/ARCHITECTURE.md` | техническая конституция и единственный действующий архитектурный закон |
| `docs/adr/` | архитектурные решения и архитектурная история |
| `docs/DOCUMENTATION_BASELINE.md` | зафиксированное состояние документационного контура |
| GitHub Issues | утверждённые задания, рабочие требования, фиксация находок и решений |
| Pull Requests | предлагаемые изменения и контекст ревью |
| commits и смерженная история | фактическая запись изменений |
| каноническая документация | зафиксированное текущее состояние проекта |

Разговоры в чатах (включая ChatGPT) **не заменяют** фиксацию в GitHub.
Устное решение не является частью проекта до его записи в GitHub.

---

## 3. Роли

### 3.1. ChatGPT — Архитектор / Технический руководитель

ChatGPT действует как архитектор, технический руководитель и ревьюер.

**Обязанности:**

- определять и уточнять цели работы;
- декомпозировать работу на исполняемые GitHub Issues;
- указывать применимые архитектурные правила и ADR;
- ревьюить предлагаемые архитектурные изменения;
- ревьють результаты Arena на соответствие архитектуре и контрактам;
- принимать решения о необходимости ADR при обнаружении архитектурного gap;
- принимать, отклонять или запрашивать исправление результатов;
- осуществлять архитектурное ревью перед ратификацией.

ChatGPT **не обходит** архитектурное управление репозитория.

### 3.2. Arena — Исполнитель

Arena действует как исполнитель реализации и верификации.

**Обязанности:**

- выполнять утверждённые GitHub Issues;
- анализировать репозиторий и каноническую документацию;
- реализовывать запрошенные изменения;
- тестировать и проверять свою работу;
- отчитываться через GitHub;
- выявлять противоречия, риски, недостающие требования и архитектурные gaps;
- предлагать изменения, когда текущая архитектура препятствует корректной реализации;
- обнаруживать и фиксировать проблемы.

**Ограничения Arena:**

- Arena **не имеет полномочий** самостоятельно ратифицировать или изменять
  архитектурные законы;
- Arena **не имеет полномочий** изменять `docs/ARCHITECTURE.md` без
  отдельного архитектурного решения;
- Arena **не имеет полномочий** выполнять merge в `main` самостоятельно;
- Arena **не может** считать устное решение частью проекта без фиксации в GitHub.

Если Arena обнаруживает необходимость изменения `ARCHITECTURE.md`, она:

1. останавливает соответствующую часть работы;
2. фиксирует gap в GitHub Issue;
3. описывает конфликт с указанием затронутого закона/раздела;
4. предлагает варианты решения;
5. при необходимости подготавливает ADR;
6. ожидает архитектурного решения;
7. продолжает реализацию только после решения.

## 4. Протокол коммуникации

Основной путь коммуникации:

```text
ChatGPT
   ↓
GitHub Issue / ADR / PR review
   ↓
Arena
   ↓
GitHub PR / Issue comment / верификационные доказательства
   ↓
ChatGPT — архитектурное ревью
```

Важные проектные решения должны быть перенесены из разговора в GitHub
до того, как они считаются проектной истиной.

---

## 5. Жизненный цикл задачи

### 5.1. Основной путь

Задача проходит следующие состояния:

```text
PROPOSED → READY → IN PROGRESS → IMPLEMENTED → REVIEW → ACCEPTED → MERGED
```

| Состояние | Описание |
|---|---|
| PROPOSED | Issue создан, ожидает уточнения и подготовки |
| READY | Issue содержит все необходимые элементы (§6), готов к исполнению |
| IN PROGRESS | Arena начала выполнение |
| IMPLEMENTED | Изменения реализованы, PR создан |
| REVIEW | Архитектурное ревью ChatGPT |
| ACCEPTED | Ревью пройдено, замечания устранены |
| MERGED | PR смержен в `main` |

Конкретные GitHub labels или состояния project board могут меняться
без изменения концептуального жизненного цикла.

### 5.2. Путь при блокировке

Если выполнение заблокировано:

```text
IN PROGRESS
   ↓
BLOCKED
   ↓
Architecture Gap зафиксирован в GitHub (§9)
   ↓
Архитектурное решение (ChatGPT / ADR)
   ↓
IN PROGRESS
```

Arena не продолжает работу над заблокированной частью до получения решения.

## 6. Стандарт задания Arena

Issue, передаваемое Arena, должно быть достаточно самодостаточным
для исполнения из GitHub без обращения к скрытому контексту чата.

Существенное Issue должно содержать:

1. **Цель** — что должно быть достигнуто.
2. **Контекст** — почему эта задача нужна сейчас.
3. **Источники истины** — применимые документы и разделы ARCHITECTURE.md, ADR.
4. **Конкретное задание** — что именно сделать.
5. **Ограничения** — что нельзя делать и почему.
6. **Критерии готовности** — как проверить, что задача выполнена.
7. **Ожидаемый результат** — что должно появиться в репозитории.

Задание должно явно указывать архитектурные ограничения, когда они применимы.

---

## 7. Стандарт Pull Request

PR, созданный Arena, должен ясно показывать:

- какое Issue он реализует;
- что изменено;
- что намеренно **не** изменено;
- что проверено;
- какие тесты или проверки выполнены;
- какая документация изменена;
- обнаружен ли архитектурный gap;
- требуется ли ADR;
- оставшиеся риски или ограничения.

PR является предлагаемым изменением до прохождения ревью и merge.

### 7.1. Шаблон описания PR

```text
## Что проверено

- ...

## Что изменено

- ...

## Что НЕ изменено

- ...

## Verification

- ...

## Risks / Gaps

- None
или
- ...

## Source of Truth

- Ссылки на ARCHITECTURE.md, ADR, DOCUMENTATION_BASELINE

## Issue

Closes #<номер>
```

---

## 8. Стандарт отчёта Arena

Arena отчитывается через GitHub, а не через недокументированный
параллельный канал.

Существенный отчёт о выполнении должен включать:

- **статус:** выполнено / заблокировано / частично;
- **что проверено** — область проверки;
- **что изменено** — конкретные файлы и изменения;
- **что намеренно НЕ изменено** — с обоснованием;
- **верификация** — результаты тестирования/проверки;
- **найденные риски** — обнаруженные проблемы;
- **обнаруженные gaps** — архитектурные или документационные пробелы;
- **ссылка на PR**;
- **итоговый статус задачи.**

Отчёт должен позволять архитектору проверить результат без обращения
к скрытому контексту Arena.

Заявление о завершении без соответствующего доказательства в GitHub
не считается достаточным проектным доказательством.

---

## 9. Протокол архитектурного gap

Если Arena обнаруживает, что корректное выполнение требует изменения
архитектурного закона, она **не должна** молча изменять закон.

Обязательный путь:

1. **Зафиксировать** проблему в GitHub (новый Issue или комментарий).
2. **Описать** конфликт или недостающее правило.
3. **Указать** затронутый архитектурный закон или раздел ARCHITECTURE.md.
4. **Предложить** минимальное жизнеспособное решение.
5. **Подготовить** ADR, если это требуется по `ARCHITECTURE.md`.
6. **Ожидать** архитектурного решения от ChatGPT / владельца проекта.
7. **Продолжить** реализацию только в рамках утверждённых правил.

Этот протокол предотвращает тихое изменение конституции под давлением
реализации.

## 10. Документационная дисциплина

Проект следует правилам документационного управления, установленным
в `ARCHITECTURE.md` и `DOCUMENTATION_BASELINE.md`.

В частности:

- одна тема — один канонический документ;
- исторические документы не конструируются предположением;
- устаревшие документы удаляются или явно выводятся из обращения
  через установленный процесс управления;
- архитектурные утверждения ссылаются на каноническую архитектуру или ADR;
- конкурирующие дубликаты запрещены.

`OPERATING_MODEL.md` является операционным документом.
Он **не должен** становиться вторым архитектурным документом.

Запрещено создание:
- `OPERATING_MODEL-final.md`;
- `OPERATING_MODEL-v2.md`;
- `OPERATING_MODEL-new.md`;
- и аналогичных конкурирующих документов.

## 11. Git Workflow

Проект использует стандартный GitHub workflow:

```text
Issue → ветка → изменения → PR → ревью → merge в main
```

### 11.1. Правила

- Рабочие изменения выполняются в отдельных ветках.
- Изменения попадают в `main` только через Pull Request.
- Каждый PR связан с Issue.
- Merge в `main` выполняется после прохождения ревью.
- Задача считается завершённой только после merge в `main`,
  а не на основании сообщения Arena.

### 11.2. Ограничения

- Arena не выполняет merge в `main` без явного подтверждения.
- Изменения должны быть проверяемы через GitHub.
- Нельзя считать задачу завершённой только по сообщению исполнителя.

---

## 12. Правило завершения

Задача считается завершённой только при выполнении **всех** условий:

- запрошенная реализация или документационная работа присутствует;
- критерии готовности выполнены;
- верификация проведена;
- необходимая документация синхронизирована;
- необходимые ADR существуют и ратифицированы, если применимо;
- результат пройден ревью;
- утверждённый PR смержен в `main`.

До merge изменение остаётся предлагаемой работой, а не истиной
репозитория на основной ветке.

---

## 13. Приоритет источников и разрешение конфликтов

При конфликте источников используется следующий приоритет:

1. Действующий `docs/ARCHITECTURE.md` — технический закон проекта.
2. Ратифицированные ADR — фиксируют архитектурное решение и его основание
   в порядке, предусмотренном ARCHITECTURE.md. ADR не заменяет и не
   переопределяет действующий текст ARCHITECTURE.md самостоятельно.
3. Действующая каноническая документация проекта.
4. Утверждённые GitHub Issues и требования PR.
5. Контекст разговора.

Если артефакт нижнего уровня конфликтует с источником более высокого
уровня, конфликт должен быть выявлен, а не тихо разрешён исполнителем.

Если обнаружен конфликт между ратифицированным ADR и действующим
`ARCHITECTURE.md`, исполнитель не выбирает трактовку самостоятельно:
он фиксирует Architecture Gap (§9), останавливает соответствующую часть
работы и ожидает архитектурного решения.

## 14. Не-цели

Этот документ **не**:

- определяет архитектуру приложения;
- выбирает технологический стек;
- авторизует преждевременное включение фабричной механики;
- заменяет управление через ADR;
- предоставляет Arena полномочия изменять архитектурный закон;
- требует механизмов реализации, не обоснованных текущей стадией проекта.

---

## 15. Начальный операционный принцип

Проект работает по одному простому правилу:

> **ChatGPT формулирует и ревьюит. GitHub фиксирует. Arena выполняет и отчитывается. GitHub сохраняет результат.**

Этот документ становится операционной проектной истиной только после
ревью и merge через стандартный процесс GitHub.
