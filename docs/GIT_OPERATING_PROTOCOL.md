# Git Operating Protocol

**Версия:** 1.1.2  
**Статус:** ACTIVE — операционная политика проекта  
**Область действия:** локальный Git, GitHub, рабочие ветки, Pull Request, CI, синхронизация локального репозитория с GitHub и поведение при пересоздании Arena-сессии.  
**Приоритет:** подчинён `docs/ARCHITECTURE.md`, `docs/adr/` и `docs/OPERATING_MODEL.md`. При конфликте действует документ более высокого приоритета.

---

## 0. Назначение

Этот документ определяет порядок работы AI-оператора проекта (Arena) с локальным Git и GitHub.

Цель — обеспечить согласованность, проверяемость и сохранность истории проекта и исключить автоматическое выполнение опасных операций.

Документ описывает **реальные границы среды Arena**, но не должен рассматриваться как описание только одной конкретной версии платформы. Текущие ограничения среды указываются отдельно и могут изменяться без изменения основных правил политики.

Если этап технически невыполним, Arena не имитирует его выполнение, а явно сообщает об ограничении.

---

## 1. Роли и полномочия

### 1.1. Arena — технический оператор Git/GitHub

Arena выполняет:

- диагностику локального репозитория;
- `git fetch origin` и сравнение refs, когда remote доступен;
- работу в назначенной Arena-сессией рабочей ветке;
- внесение согласованных изменений;
- локальные проверки;
- создание коммитов;
- обычный push назначенной рабочей ветки;
- создание и сопровождение Pull Request;
- чтение состояния CI;
- исправление причин failed CI новыми коммитами, если исправление находится в пределах согласованной задачи;
- post-merge проверку состояния `origin/main`;
- отчёт о фактическом состоянии репозитория.

Arena **не выполняет самостоятельно**:

- merge в `main`;
- архитектурную классификацию изменений как «значимых» или «незначимых»;
- создание, переименование или удаление веток, если это запрещено возможностями текущей среды;
- обход ограничений GitHub App или платформы;
- опасные операции из §10.

Merge выполняет владелец проекта. Если владелец намеренно делегирует конкретный merge Arena, это должно быть отдельным адресным поручением на конкретный PR и SHA; такое разрешение не становится постоянным полномочием Arena и не переносится между сессиями.

### 1.2. Владелец проекта

Владелец проекта:

- принимает архитектурные решения;
- утверждает существенные изменения;
- определяет источник истины в спорных ситуациях;
- принимает решения по конфликтам и опасным операциям;
- выполняет финальный merge либо явно делегирует конкретный merge по правилам §10.

Arena не подменяет владельца в вопросах архитектуры и проектной политики.

### 1.3. Ограничения среды Arena

Ограничения конкретной среды могут включать:

- закрепление сессии за веткой, назначенной платформой;
- эфемерный checkout, пересоздаваемый между сессиями;
- GitHub App authentication вместо пользовательской учётной записи;
- отсутствие части GitHub API permissions;
- отсутствие права создавать или переключать произвольные ветки;
- отсутствие права изменять `.github/workflows/*`;
- отсутствие доступа к GitHub Actions runners.

Arena обязана проверять фактические возможности текущей сессии и не предполагать наличие прав, которых она не может подтвердить.

Текущие ограничения среды не являются архитектурным законом проекта.

## 2. Главный рабочий цикл

Стандартный цикл:

```text
inspect → fetch → compare → plan → change → verify
  → fetch (повторно) → commit → push → PR → CI
  → owner review → owner approval → merge
  → post-merge verify → report
```

`branch` в этом цикле означает **использование доступной рабочей ветки**, а не обязательное создание новой ветки Arena.

Arena не считает задачу завершённой только потому, что создан PR. После merge необходимо подтвердить состояние `origin/main` свежей remote-проверкой.

---

## 3. Правило №1: сначала диагностика

Перед началом значимой работы Arena должна определить состояние checkout и remote:

```bash
git status --short --branch
git branch -vv
git log -1 --oneline --decorate
git rev-parse --is-shallow-repository
git fetch origin
git rev-parse HEAD origin/main
git merge-base HEAD origin/main
git rev-list --left-right --count HEAD...origin/main
git diff --stat origin/main
```

После `fetch` фиксируются:

- SHA `HEAD`;
- SHA `origin/main`;
- base-commit текущей сессии, если он известен;
- ahead/behind;
- dirty/clean working tree;
- shallow/grafted состояние.

Если `fetch` невозможен, Arena обязана явно сообщить об этом и не выдавать локальные `origin/*` refs за актуальное состояние GitHub.

---

## 4. Локальный репозиторий

### 4.1. Рабочее дерево

Незакоммиченные изменения неизвестного происхождения не удаляются, не откатываются, не перезаписываются и не коммитятся до установления их происхождения и назначения.

Наличие файла или изменения в рабочем дереве **не является доказательством**, что оно должно попасть в commit.

### 4.2. `main`

`main` — интеграционная ветка проекта. Обычная работа выполняется через рабочую ветку и PR.

После merge эталонным удалённым состоянием является `origin/main` после свежего `fetch`.

В постоянном локальном checkout владельца желаемое состояние:

```text
local main == origin/main
working tree == clean
upstream == origin/main
```

В закреплённой Arena-сессии локальный `main` может быть техническим временным ref и не является отдельным источником истины.

---

## 5. Рабочие ветки

В постоянном checkout самостоятельная задача обычно выполняется в отдельной рабочей ветке.

В Arena-сессии рабочая ветка может быть назначена платформой. Arena использует её и не обходит это ограничение.

Если Arena не может создать, переключить, переименовать или удалить ветку из-за ограничений среды, она сообщает об этом владельцу.

Правило именования веток относится к проектному процессу в целом; Arena не должна имитировать создание ветки, если платформа его не разрешает.

Рабочая ветка не используется как скрытая замена `main`.

---

## 6. Коммиты

Коммит должен:

- содержать логически связанный набор изменений;
- иметь понятное сообщение;
- пройти необходимые локальные проверки;
- не содержать случайных или посторонних изменений;
- иметь установленное происхождение всех включённых файлов.

После публикации коммита исправления выполняются новыми коммитами. `amend` и `rebase` опубликованной истории запрещены без отдельного адресного разрешения владельца.

---

## 7. Push

Разрешён только обычный push назначенной рабочей ветки.

Непосредственно перед push Arena должна повторно выполнить `git fetch origin`.

Если `origin/main` изменился относительно base сессии, Arena должна зафиксировать это в отчёте и проверить, влияет ли изменение на текущую работу.

По умолчанию для обновления опубликованной рабочей ветки предпочтителен обычный merge `origin/main` в рабочую ветку, а не rebase опубликованных коммитов. При конфликте или неопределённости Arena останавливается и передаёт решение владельцу.

Запрещены:

- force push любого вида;
- push в `main`;
- push в чужую ветку;
- удаление remote-ветки через push.

Отказ GitHub по правам не обходится. Arena сообщает точную причину и предлагает безопасный следующий шаг.

---

## 8. Pull Request и CI

PR — основной механизм интеграции изменений в `main`.

Перед созданием или обновлением PR Arena должна:

- выполнить свежий `fetch`;
- проверить base = `main`;
- проверить head = назначенная рабочая ветка;
- проверить фактический diff против актуального `origin/main`;
- выполнить необходимые локальные проверки;
- убедиться, что требуемые CI-проверки подключены.

Перед push и перед созданием/обновлением PR SHA `origin/main` должен быть проверен повторно.

После создания PR Arena отслеживает его состояние и CI.

При failed CI Arena может исправлять причину новыми коммитами в рамках согласованной задачи.

Запрещено:

- использовать `[skip ci]` для сокрытия результата проверки;
- ослаблять тесты или линтеры ради прохождения CI;
- удалять тесты ради прохождения CI;
- менять workflow ради обхода проверки;
- обходить обязательные проверки и правила репозитория.

Изменения `.github/workflows/*` выполняются только по отдельному указанию владельца и через установленный PR-процесс.

PR создан ≠ PR одобрен ≠ PR слит.

## 9. Merge и post-merge

### 9.1. Merge

Merge в `main` выполняется только через Pull Request.

Arena не выполняет merge самостоятельно и не определяет, является ли изменение архитектурно значимым.

Финальный merge выполняет владелец проекта. Если владелец отдельно делегировал конкретный merge Arena, разрешение должно однозначно указывать номер PR и head SHA и действует только для этой операции.

### 9.2. Post-merge — Arena

После предполагаемого merge Arena выполняет свежую remote-проверку:

```bash
git fetch origin
git log -1 --oneline --decorate origin/main
gh pr view <N> --json state,mergeCommit,headRefOid
```

Подтверждение merge должно опираться на состояние самого PR (`state=MERGED` и `mergeCommit`) и присутствие результата merge в `origin/main`.

Проверка ancestor исходного head SHA может использоваться дополнительно, но не является единственным универсальным критерием, поскольку при squash merge исходный head SHA не обязан быть предком `origin/main`.

Arena сообщает:

- состояние PR;
- merge commit SHA, если он есть;
- SHA `origin/main` после свежего fetch;
- подтверждено ли, что merge-результат находится в `origin/main`.

### 9.3. Post-merge — постоянный локальный checkout владельца

В постоянном checkout владельца:

```bash
git switch main
git pull --ff-only origin main
git status
```

Если `--ff-only` не проходит, локальный `main` расходится с `origin/main`; применяется §15.

В закреплённой Arena-сессии переключение на `main` не требуется и не должно имитироваться. Arena выполняет только remote-проверку из §9.2.

### 9.4. Удаление рабочей ветки после merge

Удаление рабочей ветки после merge не является автоматическим этапом Arena. Если удаление ветки желательно, оно выполняется отдельным решением владельца с учётом необходимости сохранить ссылку на историю и требований проекта.

## 10. Запрещённые операции

Без отдельного адресного письменного разрешения владельца запрещены:

- `git push --force` и `--force-with-lease`;
- `git push --delete` и `git push origin :ref`;
- переписывание опубликованной истории;
- `commit --amend` или `rebase` опубликованных коммитов;
- `filter-branch` / `filter-repo` для опубликованной истории;
- `reset --hard` для неизвестных изменений;
- `checkout -- <file>` / `restore` для неизвестных изменений;
- `clean -fd` для потенциально значимых неизвестных файлов;
- `stash drop` для неизвестной работы;
- `branch -D` или удаление значимых веток;
- удаление remote-веток;
- `reflog expire` и `gc --prune`, если они могут сделать нужные объекты недостижимыми;
- прямой push в `main`;
- merge в `main` без предусмотренного §9 разрешения владельца;
- обход или ослабление CI;
- удаление файлов ради прохождения CI;
- изменение архитектурных правил вне ADR-процесса;
- автоматическое разрешение конфликтов с риском потери данных;
- коммит файлов, происхождение которых не установлено по §12.

Общий критерий: **любая операция, после которой commit, ref или рабочие изменения могут стать недостижимыми, запрещена без явного разрешения владельца.**

Разрешение должно быть адресным: одна операция, конкретная ветка или PR, конкретный SHA и зафиксированное указание владельца. Разрешение не переносится между сессиями.

При сомнении — STOP и запрос владельцу.

---

## 11. Работа при недоступном remote

Если `fetch`, `push` или `gh` возвращают ошибку (сеть, 403, истёкший токен, недоступность GitHub App):

1. выполнять только безопасную локальную диагностику;
2. указать конкретную недоступную операцию и ошибку;
3. считать локальные `origin/*` потенциально устаревшими;
4. не утверждать состояние GitHub на основании старых refs;
5. не создавать компенсирующие коммиты;
6. сообщить владельцу, если требуется восстановление доступа или изменение разрешений.

Сценарий недоступного remote отличается от сценария пересозданного checkout и рассматривается отдельно в §12.

## 12. Начало сессии и пересозданный checkout

Каждая новая Arena-сессия рассматривается как потенциально пересозданный checkout.

Возможны следующие состояния:

- checkout создан заново;
- ветка назначена заново;
- base сессии отличается от текущего `origin/main`;
- локальные commit objects предыдущей сессии отсутствуют;
- рабочие файлы имеют содержимое относительно старого base;
- `origin/main` уже содержит более новые изменения;
- checkout является shallow/grafted.

Обязательный алгоритм **до любого коммита**:

```text
1. git fetch origin
2. определить BASE — commit, от которого создана текущая сессия, если он известен
3. определить MAIN = git rev-parse origin/main
4. сравнить BASE и MAIN
5. git status --short
6. для каждого изменённого файла сравнить его с origin/main:
   git diff origin/main -- <file>
7. проверить историю изменений файла после BASE:
   git log --oneline BASE..origin/main -- <file>
8. установить происхождение каждого изменения
9. только после этого разрешить commit/push
```

Если BASE неизвестен, Arena может вывести его как `git merge-base HEAD origin/main` и обязана явно отметить в отчёте: `base-of-session: derived`. Такой BASE является диагностическим ориентиром, а не доказательством фактического происхождения checkout.

Правила:

- если файл уже идентичен `origin/main`, его изменение не следует коммитить повторно;
- если diff относится к текущей задаче и происхождение установлено — файл является кандидатом на commit;
- если происхождение неизвестно — файл **не коммитится**;
- если `origin/main` изменил тот же файл после BASE — возможен конфликт версий; при неопределённости Arena останавливается;
- нельзя коммитить весь рабочий tree «на всякий случай»;
- нельзя восстанавливать исчезнувшие локальные commit objects, если их содержимое уже находится в GitHub;
- нельзя считать `(grafted)` доказательством потери истории GitHub.

**Источник истины по умолчанию — `origin/main` после свежего fetch. Рабочее дерево — кандидат на изменение, а не источник истины.**

Владелец может явно назначить иной источник истины для конкретного случая.

## 13. Проверка согласованности

Для постоянного локального checkout:

```bash
git rev-parse --abbrev-ref --symbolic-full-name @{u}
git rev-list --left-right --count main...origin/main
git status --short
```

`0 0` означает отсутствие ahead/behind между `main` и `origin/main`.

Нужно различать два утверждения:

- «локальный checkout согласован с имеющимся `origin/main` ref»;
- «актуальное состояние GitHub подтверждено».

Второе утверждение допустимо только после свежей remote-проверки.

## 14. Стандартный отчёт

После значимой операции Arena сообщает:

```text
Branch:          <имя>  upstream: <origin/...>
HEAD:            <SHA>  base-of-session: <SHA или unknown>
origin/main:     <SHA> (fetch: выполнен/недоступен, <время>)
Ahead/behind:    <ahead>/<behind>
Working tree:    clean | dirty (<файлы>)
Shallow/grafted: yes/no
Выполнено:       <операции>
Commits:         <SHA + сообщение>
PR:              #N <state> head=<SHA> merge=<SHA или none>
CI:              <workflow/status>
Sync result:     <результат>
Расхождения:     none | <тип по §15.1>
Недоступно:      <операции и причина>
Требуется от владельца: none | <конкретное решение>
Факты vs предположения: <явно разделить>
```

Если локальный `main` недоступен для проверки из-за ограничений Arena-сессии, это указывается явно, а не заменяется предположением.

## 15. Правило расхождения

Если локальное состояние и GitHub расходятся:

```text
STOP
→ DIAGNOSE
→ IDENTIFY SOURCE OF TRUTH
→ REPORT
→ ONLY THEN CHANGE
```

### 15.1. Матрица расхождений

| Ситуация | Диагностика | Действие Arena | Запрещено |
|---|---|---|---|
| local behind `origin/main` | `rev-list --left-right --count` | §7: проверить актуальность `origin/main`, влияние на рабочую ветку и только после этого обновлять её; в checkout владельца — `pull --ff-only` | merge в `main`, `reset --hard` |
| local ahead, unpublished | `git log origin/<branch>..HEAD` | если коммиты относятся к текущей задаче — обычный push назначенной ветки; иначе отчёт | удаление коммитов |
| diverged | `git log --graph --left-right` | STOP, показать обе стороны, ждать решения владельца | автоматический merge/rebase/reset |
| dirty working tree | `status`, `diff origin/main` | установить происхождение по §12 | commit «как есть», `restore`, `clean` |
| shallow/grafted | `--is-shallow-repository` | сообщить и работать с доступными refs; `fetch --unshallow` только при необходимости | утверждение о потере истории GitHub |
| fetch недоступен | ошибка fetch | §11 | утверждения о текущем GitHub |
| после merge PR | §9.2 | свежий fetch + проверка PR и `origin/main` | считать merge выполненным по памяти |
| base сессии != `origin/main` | сравнение BASE/MAIN | проверить затронутые файлы; при конфликте — STOP и владелец | rebase опубликованного, force push |

Если для безопасного решения требуется выбор между сохранением разных версий, Arena не выбирает самостоятельно.

---

## 16. Приоритет источников

1. фактическое состояние GitHub, подтверждённое свежим remote-запросом;
2. локальное состояние Git сразу после свежего `fetch`;
3. локальные `origin/*` без свежего fetch — потенциально устаревшие данные;
4. память сессии, чат и предположения — только контекст, не доказательство состояния Git.

Arena не принимает архитектурных решений посредством Git-операций.

Операционное изменение этого документа выполняется через PR. Изменение архитектурного закона выполняется через установленный ADR-процесс.

---

## 18. Минимальный безопасный протокол Arena

```text
Перед работой:
  status → branch -vv → log → shallow? → fetch
  → base vs origin/main → §12 при необходимости

Во время:
  назначенная ветка → изменения → проверки → diff
  → fetch → commit → push → PR → CI

После merge:
  fetch → проверить PR state/mergeCommit
  → проверить origin/main → отчёт §14
```

Невыполнимый этап не имитируется — сообщается.

## 19. Статус и изменения

Изменения этого документа выполняются через Pull Request.

Операционные изменения не требуют изменения `ARCHITECTURE.md`, если не затрагивают архитектурный закон. Архитектурные изменения проходят ADR-процесс.

Статус `ACTIVE` присваивается отдельным изменением после утверждения и merge редакции, для которой владелец подтвердил готовность документа к применению. Перевод в `ACTIVE` не должен предполагаться автоматически только из факта merge любой редакции.
