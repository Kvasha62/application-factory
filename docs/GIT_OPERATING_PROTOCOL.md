# Git Operating Protocol

**Версия:** 1.0.0  
**Статус:** DRAFT — операционная политика проекта  
**Область действия:** локальный Git, GitHub, рабочие ветки, Pull Request, CI и синхронизация локального репозитория с GitHub.  
**Приоритет:** ниже `docs/ARCHITECTURE.md` и ADR; при конфликте действует `docs/ARCHITECTURE.md`.

---

## 0. Назначение

Этот документ определяет стандартный порядок работы AI-оператора проекта с локальным Git и GitHub.

Главная цель — чтобы локальный репозиторий, GitHub и история проекта оставались согласованными, воспроизводимыми и проверяемыми, а опасные операции не выполнялись автоматически.

Документ является постоянной инструкцией для Arena и одновременно справочником для других AI-инструментов, участвующих в разработке проекта.

---

## 1. Роли

### 1.1. Arena — операционный оператор Git/GitHub

Arena отвечает за техническое ведение рабочего цикла:

- диагностику состояния локального репозитория;
- синхронизацию локальных refs с GitHub, когда соединение доступно;
- создание и ведение рабочих веток в пределах доступных ей ограничений;
- внесение согласованных изменений;
- запуск локальных проверок;
- создание коммитов;
- push рабочих веток;
- создание и сопровождение Pull Request;
- контроль CI;
- подготовку PR к merge;
- пост-merge проверку GitHub;
- синхронизацию локального `main` с `origin/main`, когда это возможно;
- отчёт о фактическом состоянии локального и удалённого репозитория.

### 1.2. Владелец проекта

Владелец проекта принимает решения по архитектуре, существенным изменениям и финальному merge защищаемых изменений.

Arena не заменяет владельца проекта в вопросах архитектурного решения.

---

## 2. Главный рабочий цикл

Стандартный цикл:

```text
inspect
  → plan
  → branch
  → change
  → verify
  → commit
  → push
  → PR
  → CI
  → approval
  → merge
  → post-merge verify
  → local sync
```

Нельзя пропускать этап диагностики перед изменением репозитория.

После merge нельзя считать работу завершённой, пока не проверено фактическое состояние `main` на GitHub и, если технически возможно, локального `main`.

---

## 3. Правило №1: сначала диагностика

Перед любой новой работой Arena должна определить:

```text
git status
git branch -vv
git log -1 --oneline --decorate
git fetch origin
```

Если `fetch` невозможен, Arena обязана явно сообщить об этом и не выдавать локальные refs за актуальное состояние GitHub.

Для важных операций дополнительно проверяются:

```text
git log --oneline --decorate --graph -15
git diff
```

и необходимые конкретные refs/commits.

---

## 4. Локальный репозиторий

### 4.1. Рабочее дерево

Перед началом задачи рабочее дерево должно быть проверено.

Если имеются незакоммиченные изменения, Arena должна установить их происхождение и назначение до начала новой работы.

Нельзя автоматически удалять, откатывать или перезаписывать неизвестные изменения.

### 4.2. `main`

`main` является основной интеграционной веткой.

Обычная работа выполняется не напрямую в `main`, а через рабочую ветку и PR.

После успешного merge эталонным удалённым состоянием является `origin/main`.

Желаемое состояние после синхронизации:

```text
local main == origin/main
working tree == clean
```

---

## 5. Рабочие ветки

Для каждой самостоятельной задачи используется отдельная рабочая ветка.

Название ветки должно быть понятным и соответствовать принятой в проекте схеме.

Если среда Arena принудительно привязывает сессию к специальной ветке, это ограничение не следует обходить. Arena должна работать в доступной ветке и явно сообщать о таком ограничении.

После завершения задачи рабочая ветка не должна использоваться как скрытая замена `main`.

---

## 6. Коммиты

Коммит должен:

- содержать логически связанный набор изменений;
- иметь понятное сообщение;
- проходить необходимые локальные проверки;
- не включать случайные или посторонние изменения.

Не следует переписывать опубликованную историю ради косметических изменений.

Если ошибка обнаружена после публикации коммита, предпочтителен новый исправляющий коммит.

---

## 7. Push

Разрешён обычный push рабочей ветки.

**Force push запрещён**, если владелец проекта явно не разрешил его для конкретной операции.

Нельзя использовать push как способ обхода PR-процесса.

Нельзя напрямую push в `main`, если проектный процесс предусматривает PR.

Если GitHub отклоняет push из-за прав приложения, Arena не должна обходить ограничение небезопасными способами. Она должна сообщить точную причину и предложить безопасный следующий шаг.

---

## 8. Pull Request

PR является основным механизмом интеграции изменений в `main`.

Перед созданием PR Arena должна проверить:

- базовую ветку;
- head-ветку;
- фактический diff;
- локальные проверки;
- наличие необходимых CI-проверок.

После создания PR Arena должна отслеживать его состояние и CI.

Merge не считается выполненным только потому, что PR был создан или CI был запущен.

---

## 9. Merge

### 9.1. Общий принцип

Merge в `main` выполняется только через Pull Request.

Для архитектурно значимых изменений требуется явное approval владельца проекта.

### 9.2. После merge

Arena должна проверить:

```text
git fetch origin

git log -1 --oneline --decorate origin/main
```

и, если имеет доступ к локальному checkout:

```text
git switch main
git pull --ff-only origin main
git status
git log -1 --oneline --decorate
```

`--ff-only` используется для безопасной синхронизации локального `main` без создания неожиданного merge-коммита.

---

## 10. Запрещённые операции

Без отдельного явного разрешения владельца проекта запрещены:

- `git push --force` / `--force-with-lease`;
- переписывание опубликованной истории;
- `git reset --hard` для неизвестных или чужих изменений;
- удаление значимых веток с незавершённой работой;
- прямой push в `main` в обход установленного процесса;
- обход обязательных CI-проверок;
- удаление файлов только ради прохождения CI;
- изменение архитектурных правил без соответствующего процесса ADR;
- автоматическое разрешение конфликтов с риском потери данных.

Если операция потенциально уничтожает работу, Arena должна остановиться и запросить решение владельца проекта.

---

## 11. Работа при недоступном GitHub

Сессия Arena может быть завершена после merge или потерять удалённый доступ.

В таком случае:

1. Arena должна продолжить только локальную диагностику, если она безопасна.
2. Она должна явно указать, что `fetch`, `push` или другие remote-операции недоступны.
3. Локальные `origin/*` refs следует считать потенциально устаревшими, если нет подтверждения их актуальности.
4. Нельзя утверждать, что GitHub имеет определённое состояние, только на основании устаревшего локального checkout.
5. Нельзя создавать компенсирующие коммиты только для устранения расхождения, происхождение которого не установлено.

---

## 12. Shallow checkout и восстановление сессии

Если после завершения сессии Arena обнаруживает:

```text
(grafted)
```

или shallow-клон, это следует рассматривать как техническое состояние среды, а не как доказательство потери истории GitHub.

В таком случае Arena должна сначала установить:

- текущий локальный commit;
- доступные `origin/*` refs;
- наличие рабочего дерева;
- наличие нужного merge-коммита на доступной ветке;
- какие commit objects действительно доступны локально.

Нельзя автоматически пытаться «восстановить» удалённые локальные commit objects, если содержимое уже находится в GitHub или рабочем дереве и происхождение состояния ещё не установлено.

---

## 13. Проверка согласованности

Для утверждения, что локальный `main` синхронизирован с GitHub, предпочтительно иметь все три условия:

```text
local main == origin/main
working tree == clean
upstream == origin/main
```

Практическая проверка:

```text
git status
git log -1 --oneline --decorate
git rev-parse main
 git rev-parse origin/main
```

Значения `main` и `origin/main` должны совпадать.

Если remote недоступен, Arena должна разделять:

- «локальный checkout согласован с имеющимся `origin/main` ref»;
- «подтверждено актуальное состояние GitHub».

Это не одно и то же.

---

## 14. Отчёт после операции

После завершения значимой Git-операции Arena должна сообщить:

1. что было сделано;
2. какой commit является результатом;
3. какая ветка изменена;
4. какой PR создан/обновлён/слит;
5. какие проверки пройдены;
6. состояние CI;
7. состояние локального `main`;
8. состояние `origin/main`;
9. чисто ли рабочее дерево;
10. требуется ли действие владельца проекта.

Отчёт должен отделять подтверждённые факты от предположений.

---

## 15. Правило расхождения

Если локальное состояние и GitHub расходятся, Arena **не должна немедленно исправлять расхождение**.

Сначала:

```text
STOP
→ DIAGNOSE
→ IDENTIFY SOURCE OF TRUTH
→ REPORT
→ ONLY THEN CHANGE
```

Особенно это относится к ситуациям после:

- merge PR;
- завершения Arena-сессии;
- пересоздания checkout;
- shallow clone;
- потери remote-доступа;
- неожиданных изменений рабочего дерева.

---

## 16. Приоритет источников

При проверке состояния проекта использовать следующий порядок доверия:

1. фактическое состояние GitHub, полученное свежей remote-проверкой;
2. фактическое состояние локального Git после свежего `fetch`;
3. локальные `origin/*` refs без свежего `fetch` — только как потенциально устаревшие данные;
4. память сессии, сообщения и предположения — только как контекст, а не как доказательство состояния Git.

---

## 17. Связь с архитектурными документами

Этот документ является операционной политикой.

Он не изменяет архитектурный закон проекта.

`docs/ARCHITECTURE.md` остаётся единственным действующим архитектурным законом, а `docs/adr/` — каталогом архитектурных решений.

Если операция Git сталкивается с архитектурным решением, Arena должна следовать архитектурным документам и установленному ADR-процессу.

---

## 18. Минимальный безопасный протокол Arena

Перед работой:

```text
1. status
2. branch -vv
3. log
4. fetch origin
5. определить базовую ветку и актуальный commit
```

Во время работы:

```text
6. отдельная рабочая ветка
7. изменения
8. проверки
9. diff
10. commit
11. push
12. PR
13. CI
```

После merge:

```text
14. проверить GitHub main
15. синхронизировать local main
16. проверить status
17. проверить commit
18. подтвердить local main == origin/main
19. выдать отчёт
```

Если любой этап невозможен из-за ограничений среды — не имитировать его выполнение, а явно сообщить об ограничении.

---

## 19. Статус и изменения документа

Изменения этого протокола сами проходят стандартный Git/PR-процесс.

Если изменение затрагивает только операционные процедуры, оно может быть оформлено как обновление этого документа.

Если изменение фактически меняет архитектурные правила проекта, оно должно быть отражено в `docs/ARCHITECTURE.md` через установленный ADR-процесс.
