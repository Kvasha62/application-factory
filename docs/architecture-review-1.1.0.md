## 1. Ответы на вопросы аудита (A–K)

### A. Контракт компонента (Component Contract)

**Текущее состояние.** §2.3 задаёт «паспорт» компонента из 8 полей (код, API, владение данными, миграции, события, контракты, тесты, документация); §30 (DoD) добавляет схему конфигурации, health/readiness, версию, владельца, информацию о совместимости; §6 описывает шесть контрактов (SSO, события, API, встраивание UI, дизайн-токены, экспорт данных/CDC); §10 — контрактное тестирование; §18 — трассируемость зависимости до конкретного контракта.

**Покрытие требуемых элементов:**

| Элемент | Статус | Где |
|---|---|---|
| API | ✅ Определён | §6.3 (OpenAPI), §7 (версионирование) |
| События | ✅ Определён | §6.2 (CloudEvents), §8 (версионирование) |
| Схемы | ✅ Определён | §9 (реестр, статусы, политика совместимости) |
| Экспорт данных / CDC | ⚠️ Частично | §6.6 — механизм есть, **контракт и его версия не определены** (F-010) |
| Протокол интеграции UI | ⚠️ Частично | §6.4 (ссылки/страницы/виджеты), §10 (props/postMessage), §21 («версионированный протокол») — **но UI не входит в паспорт компонента §2.3 и не имеет идентификатора контракта** (F-009) |
| Схема конфигурации | ✅ Определён | §20 (неизвестный ключ → BUILD ERROR) |
| Политика совместимости | ⚠️ Частично | Есть для API (§7), событий (§8), схем (§9); **нет как элемент контракта компонента** (F-008) |
| Аутентификация | ❌ Отсутствует | §27 упоминает «внешние API проходят authentication», модель не определена (F-020) |
| Авторизация | ❌ Отсутствует | Не упоминается как элемент контракта (F-021) |
| Версионирование | ✅ Определён | §7, §8, §11 |
| Объявление владения данными | ⚠️ Частично | §5 — закон, но **не объявлен как машиночитаемый элемент контракта** (F-008) |
| Граница публичного и внутреннего | ❌ Отсутствует | Нет правила «что не объявлено — то внутреннее и совместимостью не защищено» (F-008) |

**Оценка: недостаточно.** Паспорт §2.3 — это список в прозе, а не артефакт. §18 требует трассируемость каждой зависимости «до конкретного контракта», но контракт не имеет идентификатора и машиночитаемого объявления. §33 запрещает AI менять публичный контракт breaking-образом — но AI (и CI) не могут определить, где заканчивается публичный контракт.

**Минимальное дополнение (AMD-01).** Машиночитаемый **дескриптор контракта компонента** в каждой версии компонента, объявляющий: `api`, `events`, `data_export_cdc`, `ui` (протокол + версия), `configuration_schema`, `data_ownership` (с областью данных по AMD-02), `authn`, `authz`, `compatibility_policy`, `dependencies`. Правило: **всё, что не объявлено в дескрипторе, — внутренняя деталь реализации.**

### B. Модель арендатора (Tenant Model)

**Текущее состояние (§5.4 + LAW-16).** экземпляр платформы по умолчанию многоарендный (multi-tenant); арендатор — конечный клиент платформы; контекст арендатора выдаётся Identity и обязателен во всех компонентах; Level 0 — `tenant_id` + RLS; Level 1+ — допустимо физическое разделение; каждое событие, запись экспорта/CDC и трейс содержат `tenant_id`; суб-арендатор — внутреннее понятие компонента. LAW-16: нет доступа к данным чужого арендатора ни напрямую, ни через контракты без контекста арендатора.

**Проверка по требуемым пунктам:**

| Вопрос | Ответ в 1.1.0 |
|---|---|
| Кто создаёт арендатора | ❌ Не определено |
| Кто владеет арендатором | ❌ Не определено (§2.3 «один владелец» — только для компонентов) |
| Источник истины | ❌ Не определено (§5.4: «контекст выдаётся Identity» — но Identity не назван реестром арендаторов) |
| Жизненный цикл арендатора | ❌ Нет состояний |
| Контекст арендатора | ⚠️ Частично: «выдаётся Identity», но форма и способ проверки не определены |
| Распространение контекста (HTTP) | ⚠️ Не определено |
| Распространение между сервисами | ❌ Отсутствует |
| Фоновые задачи | ❌ Отсутствует (критично: у джобы нет пользователя) |
| События | ✅ §5.4 требует `tenant_id` |
| CDC | ✅ §5.4 требует `tenant_id`; ❌ но нет правила для таблиц без `tenant_id` |
| Наблюдаемость | ✅ §26 + ADR-0009 добавляет `tenant_id` |
| Кросс-арендаторные операции | ❌ Отсутствует как категория; LAW-16 их фактически запрещает |
| Удаление арендатора | ❌ Полностью отсутствует |

**Классификация областей данных и проверка на конфликт с LAW-16.**

Вводится классификация:

```text
tenant-scoped    — данные принадлежат конкретному арендатору.
                   Доступ только в проверенном tenant-контексте.
                   Область по умолчанию для всех бизнес-данных.

platform-scoped  — данные принадлежат Platform Instance, а не арендатору:
                   реестр арендаторов, platform configuration,
                   агрегированная аналитика, лицензирование.
                   Доступ по platform-контексту с явной авторизацией.

system-scoped    — данные принадлежат фабрике, а не инстансу:
                   Component Catalog, Golden Bundle registry,
                   фабричная телеметрия.
```

**Конфликтует ли с LAW-16? Нет — но LAW-16 неполон.**

LAW-16 формулирует только запрет: «нет доступа к данным чужого арендатора … без контекста арендатора». Классификация не ослабляет этот запрет — она определяет, какие данные **вообще не являются данными арендатора**. Без неё закон оставляет вне права целые сущности, которые обязательно существуют:

* реестр арендаторов (не может быть tenant-scoped — он существует до и независимо от арендатора);
* Component Catalog, реестр Golden Bundle (системные);
* конфигурация платформы;
* агрегированная аналитика §24.

**Обнаруженное противоречие F-014 (F4).** §24 требует самостоятельные аналитические продукты (Order Analytics, Course Completion Analytics, Transport Analytics), источники которых — события, CDC и экспорт, обязанные содержать `tenant_id` (§5.4). Агрегирующая аналитика по определению обрабатывает данные нескольких арендаторов. В буквальной формулировке LAW-16 у неё нет законного статуса: платформенный контекст — не «контекст арендатора» конкретного арендатора. **Это прямое противоречие между LAW-16 и §24**, и оно разрешается именно введением LAW-16a.

**Минимальное дополнение (AMD-02, AMD-03).** Tenant вводится в иерархию §2; назначается источник арендаторской идентичности — Tenant Authority (Identity по §5.4); определяется lifecycle `provisioning → active → suspended → deletion_requested → deleted`; вводится LAW-16a с тремя областями данных; распространение контекста обязательно во всех каналах; **контекст арендатора выводится из аутентифицированного субъекта, а не принимается от вызывающей стороны** (закрывает подмену tenant_id — F-015, самый прямой путь к меж-арендаторной утечке); удаление арендатора — контрактно-видимое событие.

### C. Контракт саги (Saga Contract)

**Текущее состояние.** §6.2: «межкомпонентные бизнес-процессы проектируются как саги с явными компенсациями; атомарность между компонентами не предполагается и не изображается в UI».

**Оценка: недостаточно для реализации.** Требование есть, контракта нет. Что не определено:

| Требуемый элемент | Статус в 1.1.0 |
|---|---|
| Идентификатор саги | ❌ |
| Идентификатор корреляции | ⚠️ §26 упоминает идентификаторы корреляции и запроса для наблюдаемость, но не как элемент саги |
| Идентификатор арендатора | ❌ (§5.4 не упоминает саги) |
| Идентификатор шага | ❌ |
| Состояние | ❌ (нет машины состояний) |
| Политика повторов | ❌ |
| Таймаут | ❌ |
| Компенсация | ⚠️ «явные компенсации» — требование есть; идемпотентность компенсации, порядок, обработка отказа компенсации — нет |
| Идемпотентность | ⚠️ §6.2 требует идемпотентность потребительов, но не привязывает её к шагу саги |
| Терминальное состояние | ❌ (нет понятия завершённости саги; нет обработки «зависшей» саги) |

Также не определён **владелец состояния саги** — без этого нельзя понять, кто отвечает за восстановление после сбоя.

**Минимальное дополнение (AMD-04).** Saga Contract: `saga_id`, `correlation_id`, `tenant_id` (или явная область `platform-scoped`), `step_id`, `state`, `retry_policy`, `timeout`, `compensation`, `idempotency`, `terminal_state`. Плюс правила: владелец состояния — инициатор; компенсация идемпотентна и объявлена до выполнения шага; терминальные состояния `completed`/`compensated`/`failed`; истечение таймаута → `failed` с уведомлением, а не молчаливое завершение. **Брокер и фреймворк не выбираются** (§36).

### D. Идемпотентность (Идемпотентность)

**Текущее состояние.** §6.2: доставка at-least-once; потребители обязаны быть идемпотентны; дедупликация по идентификатору события. CloudEvents (рекомендуемый конверт события) содержит поле `id`.

**Оценка: недостаточно.** Покрыт только один класс из трёх:

| Требование | Статус |
|---|---|
| Идентификатор события | ⚠️ Косвенно (CloudEvents `id`); область уникальности и формат не определены |
| Ключ дедупликации | ⚠️ «по идентификатору события» — хранение и срок не определены |
| Ключ идемпотентности | ❌ (нет для API и команд) |
| Хранилище | ❌ Где хранятся ключи дедупликации — не определено |
| Срок хранения | ❌ **Критично**: правило без срока хранения неисполнимо — «хранить вечно» невозможно, «не хранить» пропускает дубли |
| Поведение при повторной обработке | ❌ Не отделено от повторных попыток |
| Поведение при повторной попытке | ❌ |
| Поведение при дублирующей доставке | ⚠️ «идемпотентны» — но не определено, что возвращать (успех без повторной обработки / conflict) |
| Идемпотентность API | ❌ Полностью отсутствует: §7 описывает версионирование API, но не идемпотентность |
| Идемпотентность команд | ❌ Отсутствует |

**Архитектурно необходимо разделение на три класса (AMD-05):**

```text
идемпотентность событий — event_id уникален в области производителя;
                       потребитель дедуплицирует; повтор = подтверждение без
                       повторной обработки (no-op success);
                       срок хранения ключа ≥ окна повторной доставки;
                       повторная обработка (replay) — отдельная явная операция,
                       не смешивается с повторной попыткой.

идемпотентность API  — неидемпотентная по природе операция изменения состояния
                       обязана принимать Idempotency-Key; повтор с тем же ключом
                       возвращает результат первой попытки.

идемпотентность команд — команда (включая шаг саги) несёт command_id;
                       обработчик идемпотентен по command_id.
```

Общее правило: ключ генерируется **инициатором**, а не получателем; срок хранения определяется владельцем данных (§5) и покрывает окна повторов и повторной обработки.

### E. Идентичность и безопасность (Идентичность and Security)

**Текущее состояние.** §6.1: OIDC как стандарт SSO. §27: секреты не в коде и не в Manifest; минимально необходимый доступ; сервис не получает чужие DB учётные данные; внешние API проходят authentication/authorization; зависимости проверяются; security hotfix вне релизный поезд.

**Проверка различий:**

| Различие | Покрыто в 1.1.0 |
|---|---|
| Аутентификация человека | ✅ §6.1 OIDC |
| Аутентификация сервиса | ❌ Отсутствует полностью |
| Авторизация | ❌ Нет модели: не определено, где применяется решение и кто его принимает |
| Изоляция арендатора | ⚠️ LAW-16 + §5.4, но без защита от подмены и без областей данных |

**Архитектурные границы (минимальное дополнение, AMD-06):**

```text
Человек    → OIDC                 — уже закон §6.1; человек аутентифицируется федеративно.
Сервис     → идентичность сервиса — каждый сервис, фоновая задача и агент имеют собственную
                                    проверяемую идентичность, независимую от человеческой.
                                Технология — временное решение (§36).
Компонент  → авторизация          — решение о доступе принимается на границе
                                    компонента-владельца данных; компонент не доверяет
                                    непроверенным утверждениям вызывающего о правах.
Арендатор  → изоляция             — изоляция = владение данными + обязательный
                                    проверенный контекст арендатора (AMD-02, AMD-03).
```

Технология не навязывается: mTLS, OIDC client учётные данные, workload идентичность — всё это «временные решения» по §36. Закон фиксирует только **границы**, а не механизм.

### G. Жизненный цикл манифеста (Manifest Lifecycle)

**Текущее состояние.** §16: состав манифеста (component versions, бандл, images с digest, config, расширения, branding). §16.1: иммутабельность, версия 1.8 → 1.9. §17: Composer «передаёт его на валидацию». §31: DoD платформы.

**Жизненного цикла нет вообще.** Есть только иммутабельность опубликованного манифеста.

**Нужна ли последовательность `draft → validated → approved → published → deployed → superseded → retired`?** Проверка по состояниям:

| Состояние | Нужно? | Обоснование |
|---|---|---|
| `draft` | ✅ | Composer формирует манифест (§17) до публикации |
| `validated` | ✅ | §17 прямо требует валидация; результат должен быть зафиксирован, иначе «проверено» неотличимо от «не проверено» |
| `approved` | ✅ | §31 допускает продакшен со статусом несертифицированный — значит, нужен записанный утверждающий и основание |
| `published` | ✅ | Уже де-факто в §16.1 (иммутабельность) |
| `deployed` | ✅ | §13 требует отката на предыдущий манифест; §29 — canary и observation. Без признака «развёрнут в окружении X» нельзя знать, что откатывать |
| `superseded` | ✅ | Иначе старый манифест неотличим от актуального |
| `retired` | ✅ | Нужен для вывода из обращения и для раздела 1.J (жизненный цикл данных) |

Последовательность **подтверждена как необходимая**, но с защитой от LAW-13: в standalone-режиме (§4.1) полный цикл избыточен. Упрощённый профиль: `draft → approved → published → deployed → superseded`, где `validated` и `approved` объединяются в одну записанную аттестацию.

**Не определено (дополнительно):** иммутабельность — определена (§16.1); **утверждение** — нет; **публикация** — нет (кто публикует, куда); **свидетельство развёртывания** — нет; **откат** — §13 описан как процесс, но не как состояние манифеста; **отзыв** — отсутствует полностью.

**Минимальное дополнение (AMD-08):** жизненный цикл + упрощённый профиль + требования к содержимому (`manifest_id`, version, digest, predecessor, ссылка на бандл по digest) + явная операция отзыва.

### H. Golden Bundle

**Текущее состояние.** §14: сертифицированный набор конкретных версий; порядок создания (выбор стабильных версий → матрица совместимости → контрактные тесты → E2E → миграционные пути → smoke/load → подпись → публикация). §10: без контрактных тестов компонент не попадает в Сертифицированный Golden Bundle. §15: матрица совместимости. LAW-10.

**Что означает «Сертифицированный Golden Bundle» — не определено.** Не указаны: кто сертифицирует, состав доказательств, иммутабельность, статусы, отзыв.

**Минимально необходимое содержимое (проверка каждого пункта):**

| Элемент | Статус в 1.1.0 | Комментарий |

### J. Жизненный цикл данных (Data Lifecycle)

**Текущее состояние.** §5: компонент владеет своими данными и их жизненным циклом. §19: состояние `retired` у компонента. §16: пример конфигурации `analytics: retention-days: 180`. §24: аналитика — потребитель контрактов.

| Вопрос | Статус |
|---|---|
| срок хранения (retention) | ⚠️ Только как пример конфигурации (`retention-days`) — **законом не является** |
| удаление (удаление) | ❌ Нет правила |
| удаление арендатора (tenant удаление) | ❌ Нет |
| вывод компонента из обращения (component retirement) | ❌ §19 имеет состояние `retired`, но нет правила о судьбе данных |
| срок хранения событий (event retention) | ❌ Нет (критично для повторной обработки по AMD-05) |
| срок хранения аудита (audit retention) | ❌ Нет; **аудита как требования нет вообще** (§27) |
| архивирование | ❌ Нет |

**Оценка: текущая архитектура не закрывает жизненный цикл данных.** Фраза §5 «компонент владеет жизненным циклом данных» задаёт владельца, но не задаёт правил. Практическое следствие: при удалении арендатора каждый компонент удалит (или не удалит) свои данные по-своему, и «сиротские» данные арендатора останутся в компонентах, которые не получили или не обработали событие.

**Минимальное дополнение (AMD-11).** Правила без конкретных сроков: владелец объявляет срок хранения, архивирование и удаление в контракте; удаление арендатора и вывод компонента — **контрактно-видимые события**; срок хранения событий покрывает окно восстановления и повторной обработки; аудиторские записи иммутабельны и живут дольше операционных; `retired` (§19) требует записанного решения о судьбе данных. Конкретные сроки — конфигурация/политика (§20, §36), а не конституция.

**Критический раздел. Текущее состояние: механизма нет.**

В ARCHITECTURE.md 1.1.0 **ни одно слово не сказано о том, как закон проверяется**. | Правило | Автоматизируемо сейчас? | Подход (без привязки к стеку) |

| Запрещённые импорты (нарушение границ компонентов) | ✅ Да, как только появится ≥2 компонента | Правило запрета импортов между пакетами компонентов; существуют зрелые инструменты для большинства языков (import-linter, dependency-cruiser, eslint boundaries, ruff/flake8-plugins) |

| Отсутствие контекста арендатора | ✅ Частично | Статическая проверка: запросы к таблицам из `tenant-scoped` без фильтра по `tenant_id`; наличие RLS-политик в миграциях; наличие `tenant_id` в конверт события события (schema) |
| Breaking API | ✅ Да | Diff OpenAPI: удаление, переименование, ужесточение → требуется major (§7) |
| Отсутствие контрактных тестов | ✅ Да | Проверка наличия контрактные тесты и их запуска в пайплайне публикации (§10) |
| Некорректные миграции | ✅ Частично | Проверка только вперёд: разрушительный DDL без фазы `contract`; проверка пути N-3 → N (§12.4); парная проверка expand/migrate/contract |
| Необъявленные зависимости | ✅ Да | Сверка объявленных зависимостей в дескрипторе контракта компонента с фактическими импортами и вызовами; расхождение → ошибка (§18) |

**Что НЕ автоматизируется и остаётся ручное ревью:**

* корректность бизнес-границы (LAW-01) и выбор владельца данных (LAW-03);
* обоснованность fork (§22) и перехода уровня зрелости (§4);
* оценка гейтов фабричного режима (§4.1);
* исключения из политика совместимости (§7, §8);
* авторизация кросс-арендаторных операций (AMD-02/LAW-16a);
* решения о срок хранения и архивировании (AMD-11);
* введение нового компонента в каталог (§23, правило двух использований);
* обратимость решения (LAW-15).

**Минимальное дополнение (AMD-12).** На уровне конституции фиксируется только принцип: каждое машино-проверяемое правило должно иметь механизм исполнения (автопроверка / контрактный тест / записанный ручное ревью), а правила без механизма явно перечисляются в матрице соответствия. Выбор инструментов — реализация (уровень A), а не конституция (§36, LAW-13).

### F-001 — RATIFIED 1.1.0 без существующего ADR-0009 и каталога docs/adr/

**Серьёзность:** Высокая
**Классификация:** F5 — Пробел исполнения (Operational Gap)
**Расположение:** §34, §41; `docs/adr/`

**Проблема.** §41 объявляет версию 1.1.0 **RATIFIED** со ссылкой на ADR-0009. §34 требует Level D-изменения проводить через ADR и задаёт каталог `docs/adr/`. Ни каталога, ни файла ADR-0009 в репозитории нет.

**Почему это важно.** Статус RATIFIED означает «принято по процедуре». Если записи процедуры нет, статус не подтверждён: любой может оспорить любой закон 1.1.0, и §40 («обнаружено → обосновано → ADR → проверено → ратифицировано») теряет силу как прецедент. Это подрывает весь механизм защиты от расползания архитектуры.

**Доказательство.** `ls docs/` → только `ARCHITECTURE.md`. `git log --all --diff-filter=A --name-only` → 12 файлов, ADR отсутствует. Текст §41: «| 1.1.0 | **RATIFIED** | ADR-0009: … |».

**Рекомендация.** Восстановить ADR-0009 по фактическому содержанию 1.1.0 либо явно пометить его как утерянный; добавить в закон правило: версия считается RATIFIED только при наличии ADR-файла, на который ссылается changelog (AMD-12). Создать `docs/adr/`.

**Требует ADR:** Да (AMD-12, правило о доказательстве ратификации)
**Требует изменения кода:** Нет
**Требует изменения документации:** Да

### F-008 — Публичный Component Contract не формализован как артефакт

**Серьёзность:** Высокая
**Классификация:** F2 — Архитектурный пробел (Architectural Gap)
**Расположение:** §2.3, §6, §18, §30

### F-014 — Противоречие: LAW-16 запрещает кросс-арендаторный доступ, §24 его требует

**Серьёзность:** Высокая
**Классификация:** F4 — Противоречие (Contradiction)
**Расположение:** LAW-16 (§38) ↔ §24, §5.4

**Проблема.** LAW-16: «нет доступа к данным чужого арендатора ни напрямую, ни через контракты без контекста арендатора». §24 требует самостоятельные аналитические продукты (Order Analytics и др.) на основе событий, CDC и export — все они по §5.4 обязаны содержать `tenant_id`, т.е. являются tenant-scoped. Агрегирующая аналитика по определению обрабатывает данные нескольких арендаторов; платформенный контекст не является «контекстом арендатора» конкретного арендатора. Значит, законная аналитика по §24 формально нарушает LAW-16.

**Почему это важно.** Это единственное найденное прямое логическое противоречие внутри конституции. Оно разрешается на практике произвольно: кто-то «закроет глаза» на LAW-16, кто-то откажется от аналитики. Оба исхода плохи. Та же проблема у реестра арендаторов, Component Catalog, реестр Golden Bundle и конфигурация платформы — у них нет законной категории данных.

**Доказательство.** LAW-16 (§38) — цитата выше. §24: «Поэтому возможны самостоятельные продукты: Order Analytics; Course Completion Analytics; Transport Analytics; Blog Attendance Analytics». §5.4: «каждое событие, экспорт/CDC-запись и трейс содержат tenant_id». В документе нет ни термина `platform-scoped`, ни исключений для агрегации.

**Рекомендация.** AMD-02 + LAW-16a: ввести классификацию `tenant-scoped` / `platform-scoped` / `system-scoped`; каждый набор данных в `data_ownership` относится ровно к одной области; кросс-арендаторные операции допустимы только над platform/system-scoped данными с записью авторизации в аудите. Запрет доступа к данным чужого арендатора **не ослабляется**.

**Требует ADR:** Да (обязательно — изменение LAW-16, §35)
**Требует изменения кода:** Да (объявление области данных в контракте)
**Требует изменения документации:** Да

### F-015 — Нет запрета доверять контексту арендатора, переданному вызывающей стороной

**Серьёзность:** Критическая
**Классификация:** F2 — Архитектурный пробел (Architectural Gap)
**Расположение:** §5.4, §27, LAW-16

**Проблема.** Закон требует наличия контекста арендатора, но не требует, чтобы контекст был **производным от аутентифицированного субъекта**. Компонент, принимающий `tenant_id` из заголовка/поля запроса, формально соблюдает §5.4 (контекст присутствует) и LAW-16 (доступ «в контексте арендатора»), но по существу реализует полное отсутствие изоляции: любой клиент читает данные любого арендатора, подставив `tenant_id`.

**Почему это важно.** Самый прямой и наиболее вероятный путь к меж-арендаторной утечке. LAW-16 без этого правила защищает только от честных вызывающих. В модели «Level 0 + RLS» это единственный слой защиты, и он держится на соглашении, а не на законе.

**Доказательство.** §5.4: «контекст арендатора выдаётся Identity и обязателен во всех компонентах». Нигде не сказано, что компонент обязан **проверить** контекст против аутентифицированного субъекта и не вправе принимать его от вызывающей стороны. §27 содержит общие требования, но не это.

**Рекомендация.** AMD-03: контекст арендатора выводится из проверенного токена/идентичности сервиса; `tenant_id` от вызывающей стороны используется только для сверки и отклоняется при несовпадении; исключения — только для явно platform-scoped операций. Приравнять нарушение к нарушению LAW-16.

**Требует ADR:** Да (AMD-03; расширяет LAW-16)
**Требует изменения кода:** Да (проверка на границе каждого компонента; автопроверка в CI)
**Требует изменения документации:** Да

**Классификация:** F2 — Архитектурный пробел (Architectural Gap)
**Расположение:** §5.4, §5, §19

**Проблема.** У Law-16 и §5.4 есть правила изоляции, но нет правил прекращения существования арендатора. Кто инициирует удаление, как оно распространяется по компонентам, что происходит с данными, как подтверждается завершение — не определено.

**Почему это важно.** Прямое следствие LAW-03: каждый компонент владеет своими данными, значит удаление арендатора — это N независимых операций в N компонентах. Без контрактно-видимого события удаления компоненты оставят «сиротские» данные удалённого арендатора — нарушение изоляции и, как правило, нарушение обязательств по обработке данных.

**Доказательство.** Поиск по документу: слова «удаление», «удаление» применительно к арендатору отсутствуют. §5.4 заканчивается на суб-арендаторе.

**Рекомендация.** AMD-02 (состояние `deletion_requested → deleted`) + AMD-11 (удаление — контрактно-видимое событие жизненного цикла; потребители обязаны обработать; должно быть проверяемо).

**Требует ADR:** Да (AMD-02, AMD-11)
**Требует изменения кода:** Да
**Требует изменения документации:** Да

### F-017 — Терминологическая коллизия «клиент»: Platform Instance или Tenant?

**Серьёзность:** Средняя
**Классификация:** F1 — Уточнение формулировки (Clarification)
**Расположение:** §2.2, §39, §5.4

**Проблема.** §2.2: Platform Instance — «конкретный развёрнутый продукт заказчика». §39: Platform Manifest → Customer A / Customer B / Customer C. §5.4: арендатор — «конечный клиент платформы (магазин, школа)». Одно слово «клиент» обозначает два разных уровня: владельца инстанса и арендатора внутри инстанса.

**Почему это важно.** От этого зависит, что именно идентифицирует `platform_id` и что — `tenant_id`, и как применять §26 (телеметрия «Platform + tenant_id»). Ошибка на этом уровне приводит к построению отдельного инстанса на каждый магазин (разрушает экономику фабрики) либо к отсутствию изоляции между магазинами.

**Рекомендация.** Ввести различение: **Customer = владелец Platform Instance**; **Tenant = арендатор внутри инстанса**. Явно указать, что одноарендный инстанс (один tenant на инстанс) — допустимое частное состояние, а не отдельная модель. Дополнить §2.2 и §39.

**Требует ADR:** Нет (уточнение терминологии в рамках AMD-02)

### F-018 — Saga Contract не определён

### F-019 — Модель идемпотентности неполна

**Серьёзность:** Высокая
**Классификация:** F2 — Архитектурный пробел (Architectural Gap)
**Расположение:** §6.2, §7

**Проблема.** Покрыта только event-идемпотентность, и то частично: не определены область уникальности `event_id`, хранилище и **срок хранения** ключей дедупликации, семантика повторная обработка и поведения при дубле. API- и command-идемпотентность отсутствуют полностью.

**Почему это важно.** Модель at-least-once без срок хранения ключей неисполнима: хранить вечно нельзя, не хранить — дубли ломают инварианты (двойное списание, двойной заказ). §7 описывает версионирование API, но не идемпотентность операций — это означает, что повтор запроса при таймауте сети создаст второй эффект.

**Рекомендация.** AMD-05: три класса (event / API / command); ключ генерируется инициатором; срок хранения ≥ повторная попытка + повторная обработка окна, определяется владельцем данных; повторная доставка = успех без повторной обработки; повторная обработка — отдельная явная операция.

**Требует ADR:** Да (AMD-05; §35 защищает Contract model)

### F-020 — Аутентификация сервисов (межсервисный) не определена

**Серьёзность:** Высокая
**Классификация:** F2 — Архитектурный пробел (Architectural Gap)
**Расположение:** §6.1, §27

**Проблема.** §6.1 охватывает только человека (OIDC/SSO). Аутентификация сервиса, джобы, агента и внутреннего вызова не определена. §27 лишь говорит, что «внешние API проходят authentication/authorization».

**Почему это важно.** Основной трафик в компонентной платформе — сервисный, а не пользовательский. Без модели идентичность сервиса невозможно: применять LAW-04 (доступ к данным только по контракту), отличать вызов компонента от вызова злоумышленника, применять AMD-03 (проверка контекста арендатора), реализовать §27 («доступ минимально необходимый»).

**Рекомендация.** AMD-06: граница `Сервис → идентичность сервиса`; каждый сервис, задача и агент имеет собственную проверяемую идентичность, независимую от человеческой. Технология (mTLS, OIDC client учётные данные, workload идентичность) — временное решение §36, не фиксируется конституцией.

**Требует ADR:** Да (AMD-06)

### F-021 — Модель авторизации не определена

### F-023 — Жизненный цикл Platform Manifest отсутствует

### F-025 — Понятие «Сертифицированный Golden Bundle» и состав доказательств не определён

**Серьёзность:** Высокая
**Классификация:** F2 — Архитектурный пробел (Architectural Gap)
**Расположение:** §10, §14, §15, LAW-10

**Проблема.** §14 определяет Golden Bundle как «сертифицированный набор конкретных версий» и перечисляет **процедуру** создания, но не **артефакт**: не определены состав обязательного содержимого, кто сертифицирует, статусы. Результаты контрактных тестов, E2E и проверки миграций выполняются, но не становятся частью бандл.

**Почему это важно.** LAW-10 объявляет бандл «сертифицированной комбинацией». Сертификация без зафиксированного состава доказательств не воспроизводима: через месяц невозможно ни подтвердить, что проверки проходили, ни повторить их, ни понять, на какой версии матрица совместимости основан бандл. §15 требует вести матрицу, но бандл на неё не ссылается.

**Доказательство.** §14: «выбираются стабильные версии; проверяется матрица совместимости; выполняются контрактные тесты; выполняется E2E; проверяются миграционные пути; выполняется smoke/load-валидация; артефакт подписывается; бандл публикуется в реестр». §10: «Закон. Компонент не может попасть в Сертифицированный Golden Bundle, если обязательные контрактные тесты не пройдены» — про условие, не про артефакт доказательств.

**Рекомендация.** AMD-09: Сертифицированный Golden Bundle = иммутабельный подписанный артефакт с `bundle_id + version + digest`, обязательно содержащий: бандл идентичность, закреплённые версии компонентов **с digest**, compatibility доказательства (с версией матрицы), contract test доказательства, migration доказательства (включая N-3 → N), E2E доказательства, digest артефактов, подпись, статус. Статусы `draft → candidate → certified → deprecated → revoked`.

**Требует ADR:** Да (AMD-09; §35 защищает Golden Bundle model)
**Требует изменения кода:** Да (схема бандла + хранилище доказательств)
**Требует изменения документации:** Да

### F-026 — Golden Bundle не имеет идентичности и иммутабельности; манифест ссылается на него по мутабельному имени

**Серьёзность:** Высокая
**Классификация:** F2 — Архитектурный пробел (Architectural Gap) (с признаками F4 против §1.3 и LAW-09)

### F-027 — Отзыв (revocation) Golden Bundle не определён

**Серьёзность:** Средняя
**Классификация:** F2 — Архитектурный пробел (Architectural Gap)
**Расположение:** §14, §28, §29

**Проблема.** У бандл нет статусов и нет процедуры отзыва. §28 допускает релиз безопасности и критический хотфикс «вне обычного релизный поезд», но не определяет, что происходит с уже сертифицированным Golden Bundle, в котором найден критический дефект.

**Почему это важно.** Без отзыва найденный уязвимый бандл остаётся «certified» и продолжает деплоиться. §29 (обновление) описывает переход вперёд, но не принудительный уход от скомпрометированного артефакта.

**Доказательство.** §14 не содержит статусов. §28: «Фабрика допускает: плановые Golden Bundle releases; релизы безопасности; критические хотфиксы». Процедуры отзыва нет.

**Рекомендация.** AMD-09: статус `revoked`; бандл со статусом `revoked` запрещён к новому деплою (CI-проверка); для уже развёрнутых инстансов требуется записанный путь перехода.

**Требует ADR:** Да (AMD-09)
**Требует изменения кода:** Да (проверка статуса при деплое)
**Требует изменения документации:** Да

### F-028 — Наблюдаемость: нет единого контекста телеметрии и правил распространения

**Серьёзность:** Средняя
**Классификация:** F2 — Архитектурный пробел (Architectural Gap) (часть полей — F1)
**Расположение:** §26, §5.4

**Проблема.** §26 задаёт минимум (Platform, Component, Version, Request/Trace ID, Environment, Timestamp, tenant_id), но не задаёт: `platform_id`, `component_id`, `correlation_id` как отдельное понятие, `saga_id`, `actor/service_id`. Требования не разделены по каналам (HTTP, события, задачи, саги, CDC). Нет правил распространения контекста и нет правила о кардинальности `tenant_id` в метриках.

**Почему это важно.** Без `correlation_id` и `saga_id` сквозная диагностика межкомпонентного процесса невозможна — а §6.2 как раз требует межкомпонентные процессы (саги). Без правил распространения контекст теряется на границе компонента. Без правила о кардинальности добавление `tenant_id` в метрику при сотнях арендаторов разрушает мониторинг — то есть буквальное исполнение §26 вредит эксплуатации.

**Доказательство.** §26: «Минимум для диагностики: Platform; Component; Version; Request/Trace ID; Environment; Timestamp». Ни одной дифференциации по каналам; про метрики и tenant_id — только «(дополнение ADR-0009: в многоарендный инстансах в этот минимум входит также tenant_id)».

**Рекомендация.** AMD-10: контекст телеметрии из 11 полей; распространение по каналам; `tenant_id` — измерение логов и трейсов, использование в метриках требует явного решения владельца; стек — временное решение §36.

**Требует ADR:** Да (AMD-10)
**Требует изменения кода:** Да
**Требует изменения документации:** Да

### F-029 — Правила жизненного цикла данных отсутствуют

**Серьёзность:** Высокая
**Классификация:** F2 — Архитектурный пробел (Architectural Gap)
**Расположение:** §5, §19, §24, §16

**Проблема.** §5 утверждает, что компонент владеет жизненным циклом своих данных, но правил не задаёт. Не определены: срок хранения, удаление, вывод компонента из обращения, срок хранения событий (нужный для повторная обработка по AMD-05), архивирование. Пример `retention-days: 180` в §16 делает срок хранения конфигурацией, а не законом.

**Почему это важно.** (1) Удаление арендатора (F-016) невозможно без правил удаления данных. (2) Срок хранения событий определяет, возможен ли повторная обработка — без него AMD-05 неисполнима. (3) §19 содержит состояние `retired`, но не говорит, что делать с данными: компонент выводится из обращения, а данные остаются без владельца.

**Доказательство.** §5: «Компонент владеет своими данными и отвечает за их жизненный цикл». §19: `… → deprecated → retired` без правил. §16: `analytics: retention-days: 180` — пример конфигурации. Разделов о срок хранения/удаление/архивирование нет.

**Рекомендация.** AMD-11: владелец объявляет срок хранения, архивирование и удаление в контракте; удаление арендатора и вывод компонента — контрактно-видимые события; срок хранения событий покрывает окно восстановления и повторной обработки; `retired` требует записанного решения о судьбе данных. Конкретные сроки — политика, не конституция.

**Требует ADR:** Да (AMD-11; затрагивает LAW-03)
**Требует изменения кода:** Да
**Требует изменения документации:** Да

### F-030 — Требование аудита (audit trail) отсутствует

**Серьёзность:** Высокая
**Классификация:** F2 — Архитектурный пробел (Architectural Gap)
**Расположение:** §27, §5.4

**Проблема.** §27 перечисляет требования безопасности, но не требует аудита действий. Между тем AMD-02 (кросс-арендаторные операции) и AMD-03 (проверка контекста арендатора) нуждаются в аудите как в механизме контроля.

**Почему это важно.** Без аудита нарушение изоляции арендаторов невозможно ни расследовать, ни доказать. Кросс-арендаторные операции (платформенная аналитика, поддержка) становятся неконтролируемыми: закон их разрешит, а проверить, кто и зачем читал данные арендатора, будет нечем.

**Доказательство.** §27: секреты, минимальный доступ, чужие учётные данные, authn/authz внешних API, проверка зависимостей, security hotfix. Слова «аудит» / «audit» нет.

**Рекомендация.** AMD-06 + AMD-11: аудиторские записи обязательны для действий, меняющих состояние или читающих данные арендатора; записи иммутабельны и сохраняются дольше операционных данных; аудит содержит actor/service_id и tenant_id.

**Требует ADR:** Да (AMD-06, AMD-11)
**Требует изменения кода:** Да
**Требует изменения документации:** Да

### F-031 — Отсутствует механизм проверки исполнения архитектурного закона

**Серьёзность:** Высокая
**Классификация:** F5 — Пробел исполнения (Operational Gap)
**Расположение:** ARCHITECTURE.md в целом; §10, §12.4, §18, §20, §32, §33

**Проблема.** В законе нет ни одного правила о том, как закон проверяется. §32/§33 адресованы разработчику и AI-агенту, но не определяют механизм контроля. §18 требует, чтобы каждая зависимость была «проверяема», но не говорит, чем. Единственная конкретика — §12.4 (CI проверяет миграционный путь). В репозитории нет CI, линтеров, схем, CODEOWNERS.

**Почему это важно.** Закон без механизма исполнения — декларация. LAW-01…LAW-16, §1.1, §1.3, §1.5, §10, §20, §27, §35 будут нарушаться постепенно и незаметно, что ровно тот процесс, от которого §40 обещает защищать. Для AI-агента (§33) отсутствие машиночитаемый правил означает, что закон исполняется только если агент его прочитал и понял.

**Доказательство.** Поиск по ARCHITECTURE.md: слова «CI» встречаются только в §12.4 и §14; «автоматическая проверка» / «соответствие» / «lint» отсутствуют. Репозиторий: нет `.github/`, `.gitlab-ci.yml`, `Makefile`, pre-commit, CODEOWNERS. `pyproject.toml` — 5 строк без инструментов.

**Рекомендация.** AMD-12 (уровень конституции): каждое машино-проверяемое правило имеет механизм исполнения — автопроверка, контрактный тест или записанный результат ручного ревью; правила без механизма перечислены в матрице соответствия; изменение уровня C/D без файла ADR не считается принятым. Инструменты — реализация (уровень A), вводятся поэтапно (см. подраздел «Возможности автоматизации»).

**Требует ADR:** Да (AMD-12)
**Требует изменения кода:** Да (поэтапно)
**Требует изменения документации:** Да

### Конституционные пробелы (Constitutional Gaps)

Только фундаментальные пробелы. Все они затрагивают пункты, защищённые §35, и вынесены в ADR-0010.

1. **Component Contract как артефакт (AMD-01)** — F-008, F-009, F-010. Публичная поверхность компонента не имеет машиночитаемого объявления; без него неисполнимы §18 (трассируемость до контракта), §30 (DoD) и §33 (запреты для AI).
2. **Tenant как сущность модели (AMD-02)** — F-011, F-012, F-013, F-016. Tenant отсутствует в иерархии §2; нет владельца, источника истины, жизненного цикла, распространения контекста, удаления.
3. **Классификация областей данных и LAW-16a (AMD-02)** — F-014. LAW-16 не оставляет законного места платформенным и системным данным; §24 противоречит LAW-16 в буквальном прочтении.
4. **Целостность контекста арендатора (AMD-03)** — F-015. Без запрета доверять tenant_id от вызывающей стороны LAW-16 не защищает от подмены контекста.
5. **Saga Contract (AMD-04)** — F-018. Требование саги есть, контракта нет.
6. **Модель идемпотентности (AMD-05)** — F-019. At-least-once без сроков хранения и семантики повторной обработки и API/command-идемпотентности неисполнима.
7. **Границы идентичности и безопасности (AMD-06)** — F-020, F-021, F-030. OIDC покрывает только человека; идентичность сервиса, авторизация и аудит не определены.
8. **Модель идентификаторов (AMD-07)** — F-022, F-024. Версия ≠ идентичность; бандл и манифест не имеют иммутабельной идентичности.
9. **Жизненный цикл манифеста (AMD-08)** — F-023, F-024. Нет состояний, утверждающего, признака развёртывания, отзыва.
10. **Сертификация Golden Bundle (AMD-09)** — F-025, F-026, F-027. Сертификация без артефакта доказательств и без иммутабельной идентичности.
11. **Контракт наблюдаемости (AMD-10)** — F-028. Нет единого контекста телеметрии и правил распространения.
12. **Жизненный цикл данных (AMD-11)** — F-029. Срок хранения/удаление/архивирование/вывод компонента не определены.
