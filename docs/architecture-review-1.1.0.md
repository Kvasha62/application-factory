## 1. Ответы на вопросы аудита (A–K)

### A. Component Contract

**Текущее состояние.** §2.3 задаёт «паспорт» компонента из 8 полей (Code, API, Data Ownership, Migrations, Events, Contracts, Tests, Documentation); §30 (DoD) добавляет configuration schema, health/readiness, version, owner, compatibility information; §6 описывает шесть контрактов (SSO, Events, API, UI Embedding, Design Tokens, Data Export/CDC); §10 — contract testing; §18 — трассируемость зависимости до конкретного контракта.

**Покрытие требуемых элементов:**

| Элемент | Статус | Где |
|---|---|---|
| API | ✅ Определён | §6.3 (OpenAPI), §7 (версионирование) |
| Events | ✅ Определён | §6.2 (CloudEvents), §8 (версионирование) |
| Schemas | ✅ Определён | §9 (registry, статусы, compatibility policy) |
| Data Export / CDC | ⚠️ Частично | §6.6 — механизм есть, **контракт и его версия не определены** (F-010) |
| UI integration protocol | ⚠️ Частично | §6.4 (links/pages/widgets), §10 (props/postMessage), §21 («версионированный protocol») — **но UI не входит в паспорт компонента §2.3 и не имеет contract id** (F-009) |
| Configuration schema | ✅ Определён | §20 (unknown key → BUILD ERROR) |
| Compatibility policy | ⚠️ Частично | Есть для API (§7), Events (§8), Schemas (§9); **нет как элемент контракта компонента** (F-008) |
| Authentication | ❌ Отсутствует | §27 упоминает «внешние API проходят authentication», модель не определена (F-020) |
| Authorization | ❌ Отсутствует | Не упоминается как элемент контракта (F-021) |
| Versioning | ✅ Определён | §7, §8, §11 |
| Data ownership declaration | ⚠️ Частично | §5 — закон, но **не объявлен как машиночитаемый элемент контракта** (F-008) |
| Public/internal boundary | ❌ Отсутствует | Нет правила «что не объявлено — то внутреннее и совместимостью не защищено» (F-008) |

**Оценка: недостаточно.** Паспорт §2.3 — это список в прозе, а не артефакт. §18 требует трассируемость каждой зависимости «до конкретного контракта», но контракт не имеет идентификатора и машиночитаемого объявления. §33 запрещает AI менять публичный контракт breaking-образом — но AI (и CI) не могут определить, где заканчивается публичный контракт.

**Минимальное дополнение (AMD-01).** Машиночитаемый **Component Contract descriptor** в каждой версии компонента, объявляющий: `api`, `events`, `data_export_cdc`, `ui` (протокол + версия), `configuration_schema`, `data_ownership` (с областью данных по AMD-02), `authn`, `authz`, `compatibility_policy`, `dependencies`. Правило: **всё, что не объявлено в descriptor'е, — внутренняя деталь реализации.**

### B. Tenant Model

**Текущее состояние (§5.4 + LAW-16).** Platform Instance по умолчанию multi-tenant; tenant — конечный клиент платформы; контекст выдаётся Identity и обязателен во всех компонентах; Level 0 — `tenant_id` + RLS; Level 1+ — допустимо физическое разделение; каждое событие, экспорт/CDC-запись и трейс содержат `tenant_id`; суб-арендатор — внутреннее понятие компонента. LAW-16: нет доступа к данным чужого арендатора ни напрямую, ни через контракты без tenant-контекста.

**Проверка по требуемым пунктам:**

| Вопрос | Ответ в 1.1.0 |
|---|---|
| Кто создаёт tenant | ❌ Не определено |
| Кто владеет tenant | ❌ Не определено (§2.3 «один владелец» — только для компонентов) |
| Source of truth | ❌ Не определено (§5.4: «контекст выдаётся Identity» — но Identity не назван реестром арендаторов) |
| Tenant lifecycle | ❌ Нет состояний |
| Tenant context | ⚠️ Частично: «выдаётся Identity», но форма и способ проверки не определены |
| Tenant propagation (HTTP) | ⚠️ Не определено |
| Service-to-service propagation | ❌ Отсутствует |
| Background jobs | ❌ Отсутствует (критично: у джобы нет пользователя) |
| Events | ✅ §5.4 требует `tenant_id` |
| CDC | ✅ §5.4 требует `tenant_id`; ❌ но нет правила для таблиц без `tenant_id` |
| Observability | ✅ §26 + ADR-0009 добавляет `tenant_id` |
| Cross-tenant operations | ❌ Отсутствует как категория; LAW-16 их фактически запрещает |
| Tenant deletion | ❌ Полностью отсутствует |

**Классификация областей данных и проверка на конфликт с LAW-16.**

Вводится классификация:

```text
tenant-scoped    — данные принадлежат конкретному арендатору.
                   Доступ только в проверенном tenant-контексте.
                   Область по умолчанию для всех бизнес-данных.

platform-scoped  — данные принадлежат Platform Instance, а не арендатору:
                   реестр арендаторов, platform configuration,
                   агрегированная аналитика, лицензирование.
                   Доступ по platform-контексту с явной авторизацией.

system-scoped    — данные принадлежат фабрике, а не инстансу:
                   Component Catalog, Golden Bundle registry,
                   фабричная телеметрия.
```

**Конфликтует ли с LAW-16? Нет — но LAW-16 неполон.**

LAW-16 формулирует только запрет: «нет доступа к данным чужого арендатора … без tenant-контекста». Классификация не ослабляет этот запрет — она определяет, какие данные **вообще не являются данными арендатора**. Без неё закон оставляет вне права целые сущности, которые обязательно существуют:

* реестр арендаторов (не может быть tenant-scoped — он существует до и независимо от арендатора);
* Component Catalog, Golden Bundle registry (системные);
* platform configuration;
* агрегированная аналитика §24.

**Обнаруженное противоречие F-014 (F4).** §24 требует самостоятельные аналитические продукты (Order Analytics, Course Completion Analytics, Transport Analytics), источники которых — события, CDC и export, обязанные содержать `tenant_id` (§5.4). Агрегирующая аналитика по определению обрабатывает данные нескольких арендаторов. В буквальной формулировке LAW-16 у неё нет законного статуса: платформенный контекст — не «tenant-контекст» конкретного арендатора. **Это прямое противоречие между LAW-16 и §24**, и оно разрешается именно введением LAW-16a.

**Минимальное дополнение (AMD-02, AMD-03).** Tenant вводится в иерархию §2; назначается Tenant Authority (Identity по §5.4); определяется lifecycle `provisioning → active → suspended → deletion_requested → deleted`; вводится LAW-16a с тремя областями данных; распространение контекста обязательно во всех каналах; **tenant-контекст выводится из аутентифицированного субъекта, а не принимается от вызывающей стороны** (закрывает подмену tenant_id — F-015, самый прямой путь к меж-арендаторной утечке); удаление арендатора — контрактно-видимое событие.

### C. Saga Contract

**Текущее состояние.** §6.2: «межкомпонентные бизнес-процессы проектируются как саги с явными компенсациями; атомарность между компонентами не предполагается и не изображается в UI».

**Оценка: недостаточно для реализации.** Требование есть, контракта нет. Что не определено:

| Требуемый элемент | Статус в 1.1.0 |
|---|---|
| Saga ID | ❌ |
| Correlation ID | ⚠️ §26 упоминает correlation/request ID для observability, но не как элемент саги |
| Tenant ID | ❌ (§5.4 не упоминает саги) |
| Step ID | ❌ |
| State | ❌ (нет машины состояний) |
| Retry Policy | ❌ |
| Timeout | ❌ |
| Compensation | ⚠️ «явные компенсации» — требование есть; идемпотентность компенсации, порядок, обработка отказа компенсации — нет |
| Idempotency | ⚠️ §6.2 требует идемпотентность консьюмеров, но не привязывает её к шагу саги |
| Terminal State | ❌ (нет понятия завершённости саги; нет обработки «зависшей» саги) |

Также не определён **владелец состояния саги** — без этого нельзя понять, кто отвечает за восстановление после сбоя.

**Минимальное дополнение (AMD-04).** Saga Contract: `saga_id`, `correlation_id`, `tenant_id` (или явная область `platform-scoped`), `step_id`, `state`, `retry_policy`, `timeout`, `compensation`, `idempotency`, `terminal_state`. Плюс правила: владелец состояния — инициатор; компенсация идемпотентна и объявлена до выполнения шага; терминальные состояния `completed`/`compensated`/`failed`; истечение таймаута → `failed` с уведомлением, а не молчаливое завершение. **Брокер и framework не выбираются** (§36).

### D. Idempotency

**Текущее состояние.** §6.2: доставка at-least-once; консьюмеры обязаны быть идемпотентны; дедупликация по идентификатору события. CloudEvents (рекомендуемый envelope) содержит поле `id`.

**Оценка: недостаточно.** Покрыт только один класс из трёх:

| Требование | Статус |
|---|---|
| Event ID | ⚠️ Косвенно (CloudEvents `id`); область уникальности и формат не определены |
| Deduplication key | ⚠️ «по идентификатору события» — хранение и срок не определены |
| Idempotency key | ❌ (нет для API и команд) |
| Storage | ❌ Где хранятся ключи дедупликации — не определено |
| Retention | ❌ **Критично**: правило без retention неисполнимо — «хранить вечно» невозможно, «не хранить» пропускает дубли |
| Replay behavior | ❌ Не отделён от retry |
| Retry behavior | ❌ |
| Duplicate delivery behavior | ⚠️ «идемпотентны» — но не определено, что возвращать (no-op success / conflict) |
| API idempotency | ❌ Полностью отсутствует: §7 описывает версионирование API, но не идемпотентность |
| Command idempotency | ❌ Отсутствует |

**Архитектурно необходимо разделение на три класса (AMD-05):**

```text
event idempotency    — event_id уникален в области производителя;
                       консьюмер дедуплицирует; повтор = подтверждение без
                       повторной обработки (no-op success);
                       retention ключа ≥ окна повторной доставки;
                       replay — отдельная явная операция, не смешивается с retry.

API idempotency      — неидемпотентная по природе операция изменения состояния
                       обязана принимать Idempotency-Key; повтор с тем же ключом
                       возвращает результат первой попытки.

command idempotency  — команда (включая шаг саги) несёт command_id;
                       обработчик идемпотентен по command_id.
```

Общее правило: ключ генерируется **инициатором**, а не получателем; retention определяется владельцем данных (§5) и покрывает retry + replay окна.

### E. Identity and Security

**Текущее состояние.** §6.1: OIDC как стандарт SSO. §27: секреты не в коде и не в Manifest; минимально необходимый доступ; сервис не получает чужие DB credentials; внешние API проходят authentication/authorization; зависимости проверяются; security hotfix вне release train.

**Проверка различий:**

| Различие | Покрыто в 1.1.0 |
|---|---|
| Human Authentication | ✅ §6.1 OIDC |
| Service Authentication | ❌ Отсутствует полностью |
| Authorization | ❌ Нет модели: не определено, где применяется решение и кто его принимает |
| Tenant Isolation | ⚠️ LAW-16 + §5.4, но без anti-spoofing и без областей данных |

**Архитектурные границы (минимальное дополнение, AMD-06):**

```text
Human    → OIDC               — уже закон §6.1; человек аутентифицируется федеративно.
Service  → Service Identity   — каждый сервис/джоба/агент имеет собственную проверяемую
                                идентичность, независимую от человеческой.
                                Технология — временное решение (§36).
Component → Authorization     — решение о доступе применяется на границе
                                компонента-владельца данных; компонент не доверяет
                                непроверенным утверждениям вызывающего о правах.
Tenant   → Isolation          — изоляция = владение данными + обязательный
                                проверенный tenant-контекст (AMD-02, AMD-03).
```

Технология не навязывается: mTLS, OIDC client credentials, workload identity — всё это «временные решения» по §36. Закон фиксирует только **границы**, а не механизм.

### F. Identifiers

**Текущее состояние.** LAW-07: «Version Everything That Matters». §11: SemVer компонента + независимые технические идентификаторы API/DB/Events. §16.1: версии манифеста 1.8 → 1.9. §8: версия схемы события.

**Оценка: единой модели идентификаторов нет.** Версия ≠ идентичность. SemVer — обещание совместимости, а не идентичность артефакта.

| Сущность | Идентификатор в 1.1.0 | Иммутабельность | Проблема |
|---|---|---|---|
| Platform | имя (`customer-platform`) | ❌ | Нет `platform_id`; §26 требует «Platform» в телеметрии |
| Component | имя (`orders`) | ❌ | Нет `component_id`; rename ломает ссылки |
| Component Version | SemVer `4.2.1` | ⚠️ | Версия ≠ идентичность поставки; digest только для образов (§1.3) |
| Manifest | номер `1.9` | ⚠️ §16.1 | Нет `manifest_id`, digest, подписи; §13 требует отката «на предыдущий манифест» |
| Golden Bundle | имя `commerce-2026.09` | ❌ | Мutable-looking; **manifest ссылается на bundle по имени без digest** (§16) → LAW-09 не обеспечен |
| Tenant | — | ❌ | Не определён |
| Event | CloudEvents `id` (рекомендация) | ⚠️ | Область уникальности не определена |
| Saga | — | ❌ | Не определён |
| Request | «correlation/request ID» (§26) | ❌ | Нет формата, нет правила перегенерации по хопу |
| Correlation | — | ❌ | Не определён |
| Contract | — | ❌ | §18 требует трассируемость «до конкретного контракта», но контракт не имеет id |

**Минимальное дополнение (AMD-07).** Разделение идентичности и версии для 11 сущностей; для поставляемых артефактов обязательна тройка `id + version + digest`. Правила генерации: иммутабелен, непрозрачен, уникален в области, **никогда не переиспользуется**, не кодирует бизнес-смысл (slug арендатора ≠ `tenant_id`), генерируется владельцем сущности. Формат (UUIDv7/ULID/другой) — временное решение §36; неизменность и уникальность — закон.

### G. Manifest Lifecycle

**Текущее состояние.** §16: состав манифеста (component versions, bundle, images с digest, config, extensions, branding). §16.1: иммутабельность, версия 1.8 → 1.9. §17: Composer «передаёт его на validation». §31: DoD платформы.

**Жизненного цикла нет вообще.** Есть только иммутабельность опубликованного манифеста.

**Нужна ли последовательность `draft → validated → approved → published → deployed → superseded → retired`?** Проверка по состояниям:

| Состояние | Нужно? | Обоснование |
|---|---|---|
| `draft` | ✅ | Composer формирует манифест (§17) до публикации |
| `validated` | ✅ | §17 прямо требует validation; результат должен быть зафиксирован, иначе «проверено» неотличимо от «не проверено» |
| `approved` | ✅ | §31 допускает production со статусом uncertified — значит, нужен записанный утверждающий и основание |
| `published` | ✅ | Уже де-факто в §16.1 (иммутабельность) |
| `deployed` | ✅ | §13 требует отката на предыдущий манифест; §29 — canary + observation. Без признака «развёрнут в окружении X» нельзя знать, что откатывать |
| `superseded` | ✅ | Иначе старый манифест неотличим от актуального |
| `retired` | ✅ | Нужен для вывода из обращения и для §J (data lifecycle) |

Последовательность **подтверждена как необходимая**, но с защитой от LAW-13: в standalone-режиме (§4.1) полный цикл избыточен. Упрощённый профиль: `draft → approved → published → deployed → superseded`, где `validated` и `approved` объединяются в одну записанную аттестацию.

**Не определено (дополнительно):** immutability — определена (§16.1); **approval** — нет; **publication** — нет (кто публикует, куда); **deployment evidence** — нет; **rollback** — §13 описан как процесс, но не как состояние манифеста; **revocation** — отсутствует полностью.

**Минимальное дополнение (AMD-08):** жизненный цикл + упрощённый профиль + требования к содержимому (`manifest_id`, version, digest, predecessor, ссылка на bundle по digest) + явная операция отзыва.

### H. Golden Bundle

**Текущее состояние.** §14: сертифицированный набор конкретных версий; порядок создания (выбор стабильных версий → compatibility matrix → contract tests → E2E → migration paths → smoke/load → подпись → публикация). §10: без contract tests компонент не попадает в Certified Golden Bundle. §15: compatibility matrix. LAW-10.

**Что означает «Certified Golden Bundle» — не определено.** Не указаны: кто сертифицирует, состав доказательств, иммутабельность, статусы, отзыв.

**Минимально необходимое содержимое (проверка каждого пункта):**

| Элемент | Статус в 1.1.0 | Комментарий |
|---|---|---|
| bundle identity | ❌ | Только имя `commerce-2026.09`; нет `bundle_id`, версии, digest |
| component versions | ✅ | §14 — закреплённые версии |
| compatibility evidence | ⚠️ | §15 требует matrix, но bundle не ссылается на её версию — доказательство не привязано к артефакту |
| contract test evidence | ⚠️ | §10 требует пройти тесты, но **не требует сохранить результат** как часть bundle |
| migration evidence | ⚠️ | §14 «проверяются migration paths», §12.4 требует путь N-3→N; результат не входит в bundle |

| artifact digests | ❌ | §1.3 требует digest для production-образов, но bundle не хранит digests компонентов — только манифест (§16) |
| signature | ✅ | §14 «артефакт подписывается» |
| status | ❌ | Нет статусов и нет отзыва |

**Минимальное дополнение (AMD-09).** Certified Golden Bundle = иммутабельный подписанный артефакт с идентичностью `bundle_id + version + digest`, обязательно содержащий все 9 элементов выше; статусы `draft → candidate → certified → deprecated → revoked`; манифест ссылается на bundle **по digest**; `revoked` запрещён к новому деплою.

### J. Data Lifecycle

**Текущее состояние.** §5: компонент владеет своими данными и их жизненным циклом. §19: состояние `retired` у компонента. §16: пример конфигурации `analytics: retention-days: 180`. §24: аналитика — потребитель контрактов.

| Вопрос | Статус |
|---|---|
| retention | ⚠️ Только как пример конфигурации (`retention-days`) — **законом не является** |
| deletion | ❌ Нет правила |
| tenant deletion | ❌ Нет |
| component retirement | ❌ §19 имеет состояние `retired`, но нет правила о судьбе данных |
| event retention | ❌ Нет (критично для AMD-05 replay) |
| audit retention | ❌ Нет; **аудита как требования нет вообще** (§27) |
| архивирование | ❌ Нет |

**Оценка: текущая архитектура не закрывает data lifecycle.** Фраза §5 «компонент владеет жизненным циклом данных» задаёт владельца, но не задаёт правил. Практическое следствие: при удалении арендатора каждый компонент удалит (или не удалит) свои данные по-своему, и «сиротские» данные арендатора останутся в компонентах, которые не получили или не обработали событие.

**Минимальное дополнение (AMD-11).** Правила без конкретных сроков: владелец объявляет retention/архивирование/удаление в контракте; удаление арендатора и вывод компонента — **контрактно-видимые события**; retention событий покрывает окно recovery/replay; аудиторские записи иммутабельны и живут дольше операционных; `retired` (§19) требует записанного решения о судьбе данных. Конкретные сроки — конфигурация/политика (§20, §36), а не конституция.

| Unpinned images | ✅ Да, полностью | Линтер манифеста/compose/values: тег `latest` или отсутствие `@sha256:` → ошибка (§1.3) |
| Missing tenant context | ✅ Частично | Статическая проверка: запросы к таблицам из `tenant-scoped` без фильтра по `tenant_id`; наличие RLS-политик в миграциях; наличие `tenant_id` в envelope события (schema) |

| Missing contract tests | ✅ Да | Проверка наличия contract tests и их запуска в пайплайне публикации (§10) |
| Invalid migrations | ✅ Частично | Проверка forward-only: destructive DDL без фазы `contract`; проверка пути N-3 → N (§12.4); парная проверка expand/migrate/contract |
| Undocumented dependencies | ✅ Да | Сверка объявленных зависимостей в Component Contract descriptor с фактическими импортами/вызовами; расхождение → ошибка (§18) |
| Violations of component boundaries | ✅ Частично | См. forbidden imports + DB access + отсутствие прямых вызовов внутренних эндпоинтов |

**Что НЕ автоматизируется и остаётся manual review:**

* корректность бизнес-границы (LAW-01) и выбор владельца данных (LAW-03);
* обоснованность fork (§22) и перехода уровня зрелости (§4);

**Минимальное дополнение (AMD-12).** На уровне конституции фиксируется только принцип: каждое машино-проверяемое правило должно иметь механизм исполнения (автопроверка / контрактный тест / записанный manual review), а правила без механизма явно перечисляются в Conformance Matrix. ### F-001 — RATIFIED 1.1.0 без существующего ADR-0009 и каталога docs/adr/

**Severity:** High
**Classification:** F5 — Operational Gap
**Location:** §34, §41; `docs/adr/`

**Problem.** §41 объявляет версию 1.1.0 **RATIFIED** со ссылкой на ADR-0009. §34 требует Level D-изменения проводить через ADR и задаёт каталог `docs/adr/`. Ни каталога, ни файла ADR-0009 в репозитории нет.

**Why it matters.** Статус RATIFIED означает «принято по процедуре». Если записи процедуры нет, статус не подтверждён: любой может оспорить любой закон 1.1.0, и §40 («обнаружено → обосновано → ADR → проверено → ратифицировано») теряет силу как прецедент. Это подрывает весь механизм защиты от расползания архитектуры.

**Evidence.** `ls docs/` → только `ARCHITECTURE.md`. `git log --all --diff-filter=A --name-only` → 12 файлов, ADR отсутствует. Текст §41: «| 1.1.0 | **RATIFIED** | ADR-0009: … |».

**Recommendation.** Восстановить ADR-0009 по фактическому содержанию 1.1.0 либо явно пометить его как утерянный; добавить в закон правило: версия считается RATIFIED только при наличии ADR-файла, на который ссылается changelog (AMD-12). Создать `docs/adr/`.

**Requires ADR:** Да (AMD-12, правило о доказательстве ратификации)
**Requires code change:** Нет
**Requires documentation change:** Да

### F-008 — Публичный Component Contract не формализован как артефакт

**Severity:** High
**Classification:** F2 — Architectural Gap
**Location:** §2.3, §6, §18, §30

**Problem.** Паспорт компонента (§2.3) — перечень в прозе, а не машиночитаемый артефакт. Нет правила, отделяющего публичную контрактную поверхность от внутренней реализации. Не являются элементами контракта: authentication, authorization, compatibility policy, область данных (AMD-02).

**Why it matters.** (1) §18 требует трассируемость каждой зависимости «до конкретного контракта» — но у контракта нет идентификатора. (2) §33 запрещает AI менять публичный контракт breaking-образом — AI не может определить границу контракта. (3) §30 DoD невозможно проверить автоматически. ### F-014 — Противоречие: LAW-16 запрещает кросс-арендаторный доступ, §24 его требует

**Severity:** High
**Classification:** F4 — Contradiction
**Location:** LAW-16 (§38) ↔ §24, §5.4

**Problem.** LAW-16: «нет доступа к данным чужого арендатора ни напрямую, ни через контракты без tenant-контекста». §24 требует самостоятельные аналитические продукты (Order Analytics и др.) на основе событий, CDC и export — все они по §5.4 обязаны содержать `tenant_id`, т.е. являются tenant-scoped. Агрегирующая аналитика по определению обрабатывает данные нескольких арендаторов; платформенный контекст не является «tenant-контекстом» конкретного арендатора. Значит, законная аналитика по §24 формально нарушает LAW-16.

**Why it matters.** Это единственное найденное прямое логическое противоречие внутри конституции. Оно разрешается на практике произвольно: кто-то «закроет глаза» на LAW-16, кто-то откажется от аналитики. Оба исхода плохи. Та же проблема у реестра арендаторов, Component Catalog, Golden Bundle registry и platform configuration — у них нет законной категории данных.

**Evidence.** LAW-16 (§38) — цитата выше. §24: «Поэтому возможны самостоятельные продукты: Order Analytics; Course Completion Analytics; Transport Analytics; Blog Attendance Analytics». §5.4: «каждое событие, экспорт/CDC-запись и трейс содержат tenant_id». В документе нет ни термина `platform-scoped`, ни исключений для агрегации.

**Recommendation.** AMD-02 + LAW-16a: ввести классификацию `tenant-scoped` / `platform-scoped` / `system-scoped`; каждый набор данных в `data_ownership` относится ровно к одной области; кросс-арендаторные операции допустимы только над platform/system-scoped данными с записью авторизации в аудите. Запрет доступа к данным чужого арендатора **не ослабляется**.

**Requires ADR:** Да (обязательно — изменение LAW-16, §35)
**Requires code change:** Да (объявление области данных в контракте)
**Requires documentation change:** Да

### F-015 — Нет запрета доверять tenant-контексту, переданному вызывающей стороной

**Severity:** Critical
**Classification:** F2 — Architectural Gap
**Location:** §5.4, §27, LAW-16

**Problem.** Закон требует наличия tenant-контекста, но не требует, чтобы контекст был **производным от аутентифицированного субъекта**. Компонент, принимающий `tenant_id` из заголовка/поля запроса, формально соблюдает §5.4 (контекст присутствует) и LAW-16 (доступ «в tenant-контексте»), но по существу реализует полное отсутствие изоляции: любой клиент читает данные любого арендатора, подставив `tenant_id`.

**Why it matters.** Самый прямой и наиболее вероятный путь к меж-арендаторной утечке. LAW-16 без этого правила защищает только от честных вызывающих. В модели «Level 0 + RLS» это единственный слой защиты, и он держится на соглашении, а не на законе.

**Evidence.** §5.4: «контекст арендатора выдаётся Identity и обязателен во всех компонентах». Нигде не сказано, что компонент обязан **проверить** контекст против аутентифицированного субъекта и не вправе принимать его от вызывающей стороны. §27 содержит общие требования, но не это.

**Recommendation.** AMD-03: tenant-контекст выводится из проверенного токена/идентичности сервиса; `tenant_id` от вызывающей стороны используется только для сверки и отклоняется при несовпадении; исключения — только для явно platform-scoped операций. Приравнять нарушение к нарушению LAW-16.

**Requires ADR:** Да (AMD-03; расширяет LAW-16)
**Requires code change:** Да (проверка на границе каждого компонента; автопроверка в CI)
**Requires documentation change:** Да

### F-016 — Удаление арендатора не определено

**Severity:** High
**Classification:** F2 — Architectural Gap
**Location:** §5.4, §5, §19

**Problem.** У Law-16 и §5.4 есть правила изоляции, но нет правил прекращения существования арендатора. Кто инициирует удаление, как оно распространяется по компонентам, что происходит с данными, как подтверждается завершение — не определено.

### F-019 — Модель идемпотентности неполна

Отсутствуют иммутабельные идентификаторы для Platform, Component, Component Version, Manifest, Golden Bundle, Tenant, Saga, Request, Correlation, Contract. Manifest не имеет id/digest; Golden Bundle идентифицируется именем `commerce-2026.09`, и манифест ссылается на него **без digest**.

**Why it matters.** (1) Воспроизводимость (LAW-09) держится на мутабельном имени bundle — это нарушает §1.3 и LAW-09 по существу. (2) §13 требует отката «на предыдущий Platform Manifest», но у манифеста нет id и признака «какой развёрнут». (3) §18 требует трассируемость до контракта, у которого нет id. (4) §26 требует correlation ID без определения его жизненного цикла.

**Evidence.** §16: `bundle: commerce-2026.09` (имя, не digest) при том, что образы закреплены как `orders@sha256:0f1e…`. §16.1: «Manifest 1.8 → 1.9 → 1.10» — только номер версии. §11: SemVer как идентификатор поставки.

**Recommendation.** AMD-07: модель идентификаторов для 11 сущностей; тройка `id + version + digest` для поставляемых артефактов; правила генерации (иммутабельность, непрозрачность, уникальность в области, запрет переиспользования, запрет кодирования бизнес-смысла); формат — временное решение §36.

**Requires ADR:** Да (AMD-07; §35 защищает Versioning law, Manifest model, Golden Bundle model)
**Requires code change:** Да

### F-023 — Жизненный цикл Platform Manifest отсутствует

**Severity:** High
**Classification:** F2 — Architectural Gap
**Location:** §16, §16.1, §17, §31

**Problem.** Определены только состав и иммутабельность опубликованного манифеста. Нет: состояний, процедуры validation (§17 упоминает её, но не фиксирует результат), утверждающего для production, признака развёртывания, признака замещения, процедуры отзыва. §31 допускает production со статусом uncertified без указания, кто это разрешил.

**Requires ADR:** Да (AMD-08; §35 защищает Manifest model)

### F-025 — Понятие «Certified Golden Bundle» и состав evidence не определены

**Severity:** High
**Classification:** F2 — Architectural Gap
**Location:** §10, §14, §15, LAW-10

**Problem.** §14 определяет Golden Bundle как «сертифицированный набор конкретных версий» и перечисляет **процедуру** создания, но не **артефакт**: не определены состав обязательного содержимого, кто сертифицирует, статусы. Результаты contract tests, E2E и проверки миграций выполняются, но не становятся частью bundle.

**Why it matters.** LAW-10 объявляет bundle «сертифицированной комбинацией». Сертификация без зафиксированного состава доказательств не воспроизводима: через месяц невозможно ни подтвердить, что проверки проходили, ни повторить их, ни понять, на какой версии compatibility matrix основан bundle. §15 требует вести матрицу, но bundle на неё не ссылается.

**Evidence.** §14: «выбираются стабильные версии; проверяется compatibility matrix; выполняются contract tests; выполняется E2E; проверяются migration paths; выполняется smoke/load validation; артефакт подписывается; bundle публикуется в registry». §10: «Закон. Компонент не может попасть в Certified Golden Bundle, если обязательные contract tests не пройдены» — про условие, не про evidence-артефакт.

**Recommendation.** AMD-09: Certified Golden Bundle = иммутабельный подписанный артефакт с `bundle_id + version + digest`, обязательно содержащий: bundle identity, закреплённые версии компонентов **с digest**, compatibility evidence (с версией матрицы), contract test evidence, migration evidence (включая N-3 → N), E2E evidence, artifact digests, signature, status. Статусы `draft → candidate → certified → deprecated → revoked`.

**Requires ADR:** Да (AMD-09; §35 защищает Golden Bundle model)
**Requires code change:** Да (bundle schema + evidence store)
**Requires documentation change:** Да

### F-026 — Golden Bundle не имеет идентичности и иммутабельности; манифест ссылается на него по мутабельному имени

**Severity:** High
**Classification:** F2 — Architectural Gap (с признаками F4 против §1.3 и LAW-09)
**Location:** §14, §16, §1.3, LAW-09, LAW-10

**Problem.** Bundle идентифицируется именем `commerce-2026.09`. Иммутабельность, версия и digest для bundle не определены. При этом §16 (манифест) ссылается на bundle **по имени без digest**, хотя образы компонентов в том же манифесте закреплены по digest.

**Why it matters.** Прямое ослабление LAW-09 (воспроизводимость): если содержимое bundle по имени `commerce-2026.09` изменится, две сборки одного и того же манифеста дадут разные платформы. Это ровно тот риск, от которого §1.3 («нельзя использовать latest как архитектурную зависимость») и фиксация по digest. Внутренняя несогласованность: в одном артефакте образы закреплены байтово, а bundle — нет.

**Evidence.** §16: `bundle: commerce-2026.09` против `orders: orders@sha256:0f1e…`. §14 не содержит требования иммутабельности или digest для bundle.

**Recommendation.** AMD-09: bundle — иммутабельный артефакт с `bundle_id + version + digest`; манифест ссылается на bundle **по digest**; CI-проверка отсутствия ссылок на bundle по имени/тегу.

**Requires ADR:** Да (AMD-09)
**Requires code change:** Да
**Requires documentation change:** Да

### F-028 — Observability: нет единого telemetry context и правил распространения

**Severity:** Medium
**Classification:** F2 — Architectural Gap (часть полей — F1)
**Location:** §26, §5.4

**Problem.** §26 задаёт минимум (Platform, Component, Version, Request/Trace ID, Environment, Timestamp, tenant_id), но не задаёт: `platform_id`, `component_id`, `correlation_id` как отдельное понятие, `saga_id`, `actor/service_id`. Требования не разделены по каналам (HTTP, события, задачи, саги, CDC). Нет правил распространения контекста и нет правила о кардинальности `tenant_id` в метриках.

**Why it matters.** Без `correlation_id` и `saga_id` сквозная диагностика межкомпонентного процесса невозможна — а §6.2 как раз требует межкомпонентные процессы (саги). Без правил распространения контекст теряется на границе компонента. Без правила о кардинальности добавление `tenant_id` в метрику при сотнях арендаторов разрушает monitoring — то есть буквальное исполнение §26 вредит эксплуатации.

**Evidence.** §26: «Минимум для диагностики: Platform; Component; Version; Request/Trace ID; Environment; Timestamp». Ни одной дифференциации по каналам; про метрики и tenant_id — только «(дополнение ADR-0009: в multi-tenant инстансах в этот минимум входит также tenant_id)».

**Recommendation.** AMD-10: telemetry context из 11 полей; распространение по каналам; `tenant_id` — измерение логов и трейсов, использование в метриках требует явного решения владельца; стек — временное решение §36.

**Requires ADR:** Да (AMD-10)
**Requires code change:** Да
**Requires documentation change:** Да

### F-029 — Правила жизненного цикла данных отсутствуют

**Severity:** High
**Classification:** F2 — Architectural Gap
**Location:** §5, §19, §24, §16

**Problem.** §5 утверждает, что компонент владеет жизненным циклом своих данных, но правил не задаёт. Не определены: retention, удаление, вывод компонента из обращения, retention событий (нужный для replay по AMD-05), архивирование. Пример `retention-days: 180` в §16 делает retention конфигурацией, а не законом.

**Why it matters.** (1) Удаление арендатора (F-016) невозможно без правил удаления данных. (2) Retention событий определяет, возможен ли replay — без него AMD-05 неисполнима. (3) §19 содержит состояние `retired`, но не говорит, что делать с данными: компонент выводится из обращения, а данные остаются без владельца.

**Evidence.** §5: «Компонент владеет своими данными и отвечает за их жизненный цикл». §19: `… → deprecated → retired` без правил. §16: `analytics: retention-days: 180` — пример конфигурации. Разделов о retention/deletion/archival нет.

**Recommendation.** AMD-11: владелец объявляет retention/архивирование/удаление в контракте; удаление арендатора и вывод компонента — контрактно-видимые события; retention событий покрывает окно recovery/replay; `retired` требует записанного решения о судьбе данных. Конкретные сроки — политика, не конституция.

**Requires ADR:** Да (AMD-11; затрагивает LAW-03)
**Requires code change:** Да
**Requires documentation change:** Да

### F-030 — Требование аудита (audit trail) отсутствует

**Severity:** High
**Classification:** F2 — Architectural Gap
**Location:** §27, §5.4

**Problem.** §27 перечисляет требования безопасности, но не требует аудита действий. Между тем AMD-02 (кросс-арендаторные операции) и AMD-03 (проверка tenant-контекста) нуждаются в аудите как в механизме контроля.

**Why it matters.** Без аудита нарушение изоляции арендаторов невозможно ни расследовать, ни доказать. Кросс-арендаторные операции (платформенная аналитика, поддержка) становятся неконтролируемыми: закон их разрешит, а проверить, кто и зачем читал данные арендатора, будет нечем.

**Requires ADR:** Да (AMD-06, AMD-11)
**Requires code change:** Да
**Requires documentation change:** Да

### F-031 — Отсутствует механизм проверки исполнения архитектурного закона

**Severity:** High
**Classification:** F5 — Operational Gap
**Location:** ARCHITECTURE.md в целом; §10, §12.4, §18, §20, §32, §33

**Problem.** В законе нет ни одного правила о том, как закон проверяется. §32/§33 адресованы разработчику и AI-агенту, но не определяют механизм контроля. §18 требует, чтобы каждая зависимость была «проверяема», но не говорит, чем. Единственная конкретика — §12.4 (CI проверяет миграционный путь). В репозитории нет CI, линтеров, схем, CODEOWNERS.

### Constitutional Gaps

Только фундаментальные пробелы. Все они затрагивают пункты, защищённые §35, и вынесены в ADR-0010.

1. **Component Contract как артефакт (AMD-01)** — F-008, F-009, F-010. Публичная поверхность компонента не имеет машиночитаемого объявления; без него неисполнимы §18 (трассируемость до контракта), §30 (DoD) и §33 (запреты для AI).
2. **Tenant как сущность модели (AMD-02)** — F-011, F-012, F-013, F-016. Tenant отсутствует в иерархии §2; нет владельца, source of truth, жизненного цикла, распространения контекста, удаления.
3. **Классификация областей данных и LAW-16a (AMD-02)** — F-014. LAW-16 не оставляет законного места платформенным и системным данным; §24 противоречит LAW-16 в буквальном прочтении.
4. **Целостность tenant-контекста (AMD-03)** — F-015. Без запрета доверять tenant_id от вызывающей стороны LAW-16 не защищает от подмены контекста.
5. **Saga Contract (AMD-04)** — F-018. Требование саги есть, контракта нет.
6. **Модель идемпотентности (AMD-05)** — F-019. At-least-once без retention, replay-семантики и API/command-идемпотентности неисполнима.
7. **Границы identity и безопасности (AMD-06)** — F-020, F-021, F-030. OIDC покрывает только человека; service identity, авторизация и аудит не определены.
8. **Модель идентификаторов (AMD-07)** — F-022, F-024. Версия ≠ идентичность; bundle и манифест не имеют иммутабельной идентичности.
9. **Жизненный цикл манифеста (AMD-08)** — F-023, F-024. Нет состояний, утверждающего, признака развёртывания, отзыва.
10. **Сертификация Golden Bundle (AMD-09)** — F-025, F-026, F-027. Сертификация без артефакта evidence и без иммутабельной идентичности.
11. **Контракт observability (AMD-10)** — F-028. Нет единого telemetry context и правил распространения.
12. **Жизненный цикл данных (AMD-11)** — F-029. Retention/удаление/архивирование/вывод компонента не определены.
13. **Исполнимость закона (AMD-12)** — F-001, F-031. Нет правила о доказательстве ратификации и о механизме проверки закона.

```text
CONSTITUTIONAL CHANGE REQUIRED
```
