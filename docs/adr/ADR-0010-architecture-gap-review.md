## Context

ARCHITECTURE.md 1.1.0 ратифицирован и объявлен техническим законом проекта (§0, §38, §41). Редакция 1.1.0 была расширена ADR-0009: добавлены гейты фабричного режима (§4.1), мультиарендность (§5.4), саги и идемпотентность (§6.2), tenant_id в observability (§26) и LAW-16 (Tenant Isolation).

Проведён аудит на предмет вопроса:

> Достаточно ли текущей конституции для безопасной реализации Platform Factory, Component Catalog, Components, Golden Bundles, Composer и Platform Instances?

Аудит проведён в три слоя:

1. **Закон** — полное чтение ARCHITECTURE.md 1.1.0 (§0–§41, LAW-01…LAW-16).
2. **Документы** — проверка существования всех файлов, на которые ссылается закон.
3. **Код** — сопоставление закона с фактическим содержимым репозитория.

**Фактическое состояние репозитория на момент аудита (commit `abb289d`):**

Всего 12 файлов. В репозитории и во всех его refs (`git log --all --diff-filter=A`) **отсутствуют**:

**Важное следствие (позитивное).** Компонентов нет, Golden Bundle нет, Platform Instances нет. Значит, **обратная совместимость ничем не ограничена**: любое уточнение конституции сейчас стоит ноль. Это «окно нулевой стоимости» закрывается в момент публикации первого компонента. Данный ADR написан именно для того, чтобы использовать это окно.

## Problem

### P1. Закон требует артефактов, формат которых не определён

Конституция оперирует сущностями, у которых нет ни идентификатора, ни структуры, ни жизненного цикла:

| Сущность | Что говорит закон 1.1.0 | Чего нет |
|---|---|---|
| Component Contract | «паспорт» из 8 полей (§2.3), DoD (§30) | машиночитаемого descriptor'а; нет authentication/authorization, UI protocol, compat policy как элементов контракта |
| Golden Bundle | «сертифицированный набор версий», «подписывается» (§14) | идентификатора, иммутабельности, digest, состава evidence, статуса, отзыва |
| Platform Manifest | состав + иммутабельность (§16, §16.1) | `manifest_id`, digest, подписи, жизненного цикла, ролей утверждения, отзыва |
| Tenant | tenant_id + RLS + LAW-16 (§5.4) | tenant как сущности в иерархии §2; владельца; source of truth; жизненного цикла; правил распространения контекста; удаления |
| Saga | «саги с явными компенсациями» (§6.2) | контракта саги: id, step, state, retry, timeout, compensation, terminal state |
| Idempotency | «дедупликация по идентификатору события» (§6.2) | модели для API и command; ключа; хранилища; retention; replay-семантики |
| Event / Saga / Request / Correlation / Contract | упоминаются по отдельности (§8, §26) | единой модели идентификаторов (LAW-07 требует «version everything that matters», но identity ≠ version) |

### P2. Закон требует механизмов, которых не существует

LAW-01…LAW-16, §1.1, §1.3, §1.5, §10, §12.4, §18, §20, §27, §35 содержат проверяемые запреты, но в ARCHITECTURE.md **нет ни одного слова о том, как закон проверяется**, а в репозитории нет ни CI, ни линтеров, ни схем, ни CODEOWNERS. Закон исполняется только на совести разработчика и AI-агента. Это классический operational gap: правило есть, механизма исполнимости нет.

### P3. Противоречие между LAW-16 и §24

LAW-16: «нет доступа к данным чужого арендатора ни напрямую, ни через контракты без tenant-контекста».

§24: Analytics — полноценные потребители контрактов; возможны самостоятельные продукты Order Analytics / Course Completion Analytics / Transport Analytics; источники — events + CDC + export, и **все они по §5.4 обязаны содержать tenant_id**.

Агрегирующая аналитика по определению читает данные более чем одного арендатора. В текущей формулировке LAW-16 такая операция не имеет законного статуса: у платформы нет категории данных, не принадлежащих конкретному арендатору. Аналогичная проблема у реестра арендаторов, Component Catalog, Golden Bundle registry и platform configuration — они не могут быть tenant-scoped, но и не описаны законом.

### P4. Ратификация 1.1.0 не подтверждена артефактами

§41 объявляет 1.1.0 **RATIFIED** со ссылкой на ADR-0009; §40 утверждает, что сценарная валидация «выполнена 2026-09-08» и что дефекты F1–F6 «устранены в базовой модели (docs/07)». Ни ADR-0009, ни docs/07, ни docs/08 в репозитории нет (F-001, F-002, F-003). Закон, который объявляет себя законом, не может ссылаться на несуществующие доказательства: это подрывает сам механизм §40 («обнаружено → обосновано → описано ADR → проверено → ратифицировано»).

### P5. Что **не** является проблемой (явно зафиксировано)

Отсутствие Component Catalog, Golden Bundles, Composer и Release Train **не является нарушением**. §4.1 прямо разрешает standalone-режим до достижения гейтов (независимо поставляемых компонентов ≥ 3 / профилей ≥ 2 / внешние потребители). Сейчас компонентов 0. Построение каталога и поездов до гейта было бы нарушением LAW-13. Текущее состояние — **соответствует закону** (finding F-034, F0).

## Decision

**Принято:** подготовить редакцию **ARCHITECTURE.md 1.2.0** как минимальное **аддитивное** расширение 1.1.0.

**Ни один существующий закон не отменяется и не меняет направления.** Не отменяется ни LAW-01…LAW-16, ни одно из правил §1.1–§1.6. Все 12 поправок либо заполняют отсутствующий уровень детализации уже существующего закона, либо вводят минимальную классификацию, без которой существующий закон неисполним.

**Не принято:** ничего не менять в реализации. Ни один микросервис, ни один брокер, ни один framework, ни одна observability-платформа не выбираются этим ADR — всё это остаётся «временными решениями» по §36 (LAW-12, LAW-13).

### AMD-01 — Component Contract descriptor

| | |
|---|---|
| **Старый закон** | §2.3: паспорт компонента (Code, API, Data Ownership, Migrations, Events, Contracts, Tests, Documentation). §30: DoD. |
| **Проблема** | Паспорт — это список в prose, а не артефакт. Нельзя автоматически проверить наличие контракта, его версию и границы публичной поверхности. |
| **Новый закон** | Публичный Component Contract объявляется **машиночитаемым descriptor'ом** в каждой версии компонента. Descriptor объявляет: `api` (OpenAPI + supported major versions), `events` (schema id + версия), `data_export_cdc` (контракт + версия), `ui` (протокол встраивания + версия протокола), `configuration_schema` (id + версия), `data_ownership` (какие данные компонент владеет), `authn` (human / service / both), `authz` (модель и где применяется), `compatibility_policy`, `dependencies` (§18). Всё, что не объявлено в descriptor'е, — **внутренняя деталь реализации, не защищённая совместимостью**. |
| **Затронутые разделы** | §2.3, §6 (новый §6.7), §18, §30, §31, §35, LAW-05, LAW-07 |

### AMD-02 — Tenant как сущность модели и классификация областей данных

| | |
|---|---|
| **Старый закон** | §5.4 (tenant_id + RLS, tenant_id в событиях/экспорте/трейсах), LAW-16 (запрет доступа к данным чужого арендатора без tenant-контекста). |
| **Проблема** | Tenant отсутствует в иерархии понятий §2. Не определены: кто создаёт, кто владеет, source of truth, жизненный цикл, распространение контекста (service-to-service, jobs, CDC), удаление. LAW-16 не оставляет законного места для данных, не принадлежащих арендатору. |
| **Новый закон** | 1. Tenant вводится в иерархию §2 как сущность уровня Platform Instance. 2. **Tenant Authority** — компонент, владеющий реестром арендаторов (по §5.4 это Identity); он создаёт tenant, присваивает `tenant_id`, владеет его жизненным циклом. 3. Жизненный цикл tenant: `provisioning → active → suspended → deletion_requested → deleted`. 4. **Классификация областей данных (новая):**<br>• `tenant-scoped` — принадлежат арендатору; доступ только в tenant-контексте; **по умолчанию для всех бизнес-данных**;<br>• `platform-scoped` — принадлежат Platform Instance, не арендатору (реестр арендаторов, platform configuration, Component Catalog, bundle registry, агрегированная аналитика, лицензирование); доступ по platform-контексту с явным authorization;<br>• `system-scoped` — принадлежат фабрике, а не инстансу (каталог компонентов, Golden Bundle registry, фабричная телеметрия).<br>Каждый набор данных в `data_ownership` компонента обязан быть отнесён ровно к одной области. Смешивание в одном наборе запрещено. 5. Кросс-арендаторные операции разрешены **только** над `platform-scoped`/`system-scoped` данными и требуют записи об авторизации в аудите (AMD-10). 6. Tenant-контекст обязателен и проверяем во всех каналах: HTTP, service-to-service, события, задачи, CDC, саги. 7. Удаление арендатора — контрактно-видимое событие (`TenantLifecycle`); каждый компонент обязан обработать его по правилам AMD-11. |
| **Конфликт с LAW-16?** | **Нет, но LAW-16 неполон.** Он задаёт только запрет. Классификация не разрешает доступ к данным чужого арендатора — она определяет, какие данные вообще не являются «данными арендатора». LAW-16 дополняется LAW-16a (ниже). |
| **Затронутые разделы** | §2 (иерархия), §5.4 (переписан), §6.2, §24, §26, §35, §36, LAW-03, **LAW-16 + новый LAW-16a** |

**LAW-16a — Data Scope Classification (новая).** Любой набор данных, которым владеет компонент, относится ровно к одной области: `tenant-scoped`, `platform-scoped` или `system-scoped`. Область объявляется в контракте компонента. Кросс-арендаторная обработка допустима только над `platform-scoped` и `system-scoped` данными.

### AMD-03 — Tenant context integrity (anti-spoofing)

| | |
|---|---|
| **Старый закон** | §5.4: «контекст арендатора выдаётся Identity и обязателен во всех компонентах». LAW-16. |
| **Проблема** | Нет запрета на доверие tenant_id, пришедшему от вызывающей стороны. Компонент, принимающий `tenant_id` из заголовка/поля запроса без проверки против аутентифицированного контекста, формально соблюдает §5.4 (tenant_id присутствует), но нарушает LAW-16 по существу. Это самый прямой путь к меж-арендаторной утечке. |
| **Новый закон** | Tenant-контекст является **производным от аутентифицированного субъекта**, а не входным параметром. Компонент обязан выводить tenant-контекст из проверенного токена/идентичности сервиса; tenant_id, переданный вызывающей стороной, может использоваться только для сверки (cross-check) и отклоняется при несовпадении. Исключения — только для явно `platform-scoped` операций. |
| **Затронутые разделы** | §5.4, §27, LAW-16a |

### AMD-04 — Saga Contract

| | |
|---|---|
| **Старый закон** | §6.2: «межкомпонентные бизнес-процессы проектируются как саги с явными компенсациями; атомарность между компонентами не предполагается и не изображается в UI». |
| **Проблема** | Требование есть, контракта нет. Нельзя реализовать сагу воспроизводимо: не определены идентификация, состояния, политика повторов, таймауты, семантика компенсации, терминальные состояния. |
| **Новый закон** | Минимальный Saga Contract, обязательный для любой саги:<br>`saga_id` · `correlation_id` · `tenant_id` (или явная область `platform-scoped`) · `step_id` · `state` · `retry_policy` · `timeout` · `compensation` · `idempotency` · `terminal_state`.<br>Дополнительные правила: владелец состояния саги — инициатор (если иное не объявлено в контракте); компенсация обязана быть идемпотентной и обязана быть объявлена до выполнения шага; терминальные состояния — `completed` / `compensated` / `failed` (из `failed` требуется явное решение); сага не считается завершённой, пока не достигнуто терминальное состояние; истечение таймаута — не молчаливое завершение, а переход в `failed` с уведомлением. **Брокер и framework не выбираются** (§36). |
| **Затронутые разделы** | §6.2, §26, §29, §35, LAW-05 |

### AMD-05 — Idempotency model

| | |
|---|---|
| **Старый закон** | §6.2: доставка at-least-once, консьюмеры идемпотентны, дедупликация по идентификатору события. |
| **Проблема** | Покрыта только event-идемпотентность. Нет: формата и области уникальности `event_id`, хранилища и retention ключей дедупликации, replay-семантики, поведения при дубле, API- и command-идемпотентности. Без retention правило неисполнимо: «хранить вечно» невозможно, «не хранить» — дубли ломают инварианты. |
| **Новый закон** | Три класса идемпотентности:<br>**1. Event idempotency** — `event_id` уникален в области производителя; консьюмер обязан дедуплицировать по `event_id`; ключ хранится не меньше максимального окна повторной доставки; повторная доставка = подтверждение без повторной обработки (no-op success); replay — отдельная явная операция, не смешивается с retry.<br>**2. API idempotency** — любая неидемпотентная по природе операция изменения состояния обязана принимать `Idempotency-Key`; повтор с тем же ключом возвращает результат первой попытки, а не создаёт второй эффект.<br>**3. Command idempotency** — команда (в т.ч. шаг саги) несёт `command_id`; обработчик обязан быть идемпотентен по `command_id`.<br>Общее: ключ идемпотентности генерируется инициатором, а не получателем; retention_key ≥ retry_window + replay_window, определяется владельцем данных (§5). |
| **Затронутые разделы** | §6.2, §7 (API), §29, LAW-05 |

### AMD-06 — Identity & Security boundaries

| | |
|---|---|
| **Старый закон** | §6.1: OIDC как стандарт SSO. §27: общие требования безопасности. |
| **Проблема** | OIDC покрывает только человека. Не определены: аутентификация сервиса, модель авторизации, место применения изоляции арендатора, аудит. |
| **Новый закон** | Четыре архитектурные границы:<br>`Human → OIDC` (уже закон, §6.1);<br>`Service → Service Identity` — каждый сервис/джоба/агент имеет собственную проверяемую идентичность, независимую от идентичности человека; технология — временное решение (§36);<br>`Component → Authorization` — решение о доступе применяется на границе компонента-владельца данных; компонент не доверяет утверждениям вызывающего о правах, не подтверждённым авторизацией;<br>`Tenant → Isolation` — изоляция обеспечивается владением данными + обязательным tenant-контекстом (AMD-02, AMD-03).<br>Плюс: действия, меняющие состояние или читающие данные арендатора, подлежат **аудиту** (AMD-11). |
| **Затронутые разделы** | §6.1, §27, LAW-16a |

### AMD-07 — Identifier model

| | |
|---|---|
| **Старый закон** | LAW-07 (Version Everything That Matters); §11 (SemVer компонента + независимые технические идентификаторы); §16.1 (версии манифеста 1.8→1.9); §8 (версия события). |
| **Проблема** | Версия ≠ идентичность. SemVer — это обещание совместимости, а не идентичность артефакта. Manifest не имеет id и digest. Golden Bundle идентифицируется именем `commerce-2026.09` — выглядит мутабельным и не закрепляет байты (нарушает LAW-09/§1.3). |
| **Новый закон** | Разделение **идентичности** и **версии** для: `platform_id`, `component_id`, `component_version_id`, `manifest_id`, `bundle_id`, `tenant_id`, `event_id`, `saga_id`, `request_id`, `correlation_id`, `contract_id`. Правила: идентификатор иммутабелен, непрозрачен, уникален в своей области, никогда не переиспользуется, не кодирует бизнес-смысл (slug арендатора ≠ tenant_id), генерируется владельцем сущности. Для поставляемых артефактов обязательна тройка `id + version + digest`. SemVer остаётся публичной версией компонента (§11), но каждая поставка дополнительно фиксируется digest (§1.3). Формат идентификатора (UUIDv7/ULID/другой) — временное решение (§36); неизменность и уникальность — закон. |
| **Затронутые разделы** | §7, §11, §14, §16, §26, LAW-07, LAW-09, LAW-10 |

### AMD-08 — Manifest lifecycle

| | |
|---|---|
| **Старый закон** | §16 (состав), §16.1 (иммутабельность, версия 1.8→1.9), §17 (Composer передаёт на validation), §31 (DoD платформы). |
| **Проблема** | Жизненного цикла нет вообще. Кто утверждает манифест для production — неизвестно. Нет признака «развёрнут» (а §13 требует отката на предыдущий манифест), нет признака «замещён»/«отозван». §31 разрешает production со статусом uncertified без указания, кто это разрешил. |
| **Новый закон** | Жизненный цикл: `draft → validated → approved → published → deployed → superseded → retired`. **Упрощённый профиль для standalone-режима (§4.1, LAW-13):** `draft → approved → published → deployed → superseded` — ступени `validated` и `approved` объединяются в одну записанную аттестацию валидации. Полный цикл обязателен только в фабричном режиме. Правила: `published` — иммутабелен (§16.1) и несёт `manifest_id + version + digest + predecessor`; переход в `approved` требует записанного утверждающего (кто + на каком основании); `deployed` фиксирует факт развёртывания в окружении (нужно для §13 и §29); `superseded` остаётся доступным для отката, но не для нового деплоя; `retired` — выведен из обращения. Отзыв (`revocation`) — отдельная явная операция, а не «молча перестали деплоить». |
| **Затронутые разделы** | §16, §16.1, §17, §29, §31, §35, LAW-09 |

### AMD-09 — Golden Bundle certification

| | |
|---|---|
| **Старый закон** | §14 (сертифицированный набор версий, порядок создания, подпись), §10 (без contract tests — не сертифицируется), §15 (compatibility matrix), LAW-10. |
| **Проблема** | «Сертифицированный» не определено: неизвестны состав доказательств, кто сертифицирует, иммутабельность, идентичность, статусы, отзыв. Манифест ссылается на bundle по имени (`commerce-2026.09`) без digest — значит, воспроизводимость (LAW-09) держится на мутабельном имени. |
| **Новый закон** | **Certified Golden Bundle** = иммутабельный, подписанный артефакт с идентичностью `bundle_id + version + digest`, обязательно содержащий: `bundle identity`; закреплённые версии компонентов **с digest артефактов**; `compatibility evidence` (ссылка на compatibility matrix и её версию); `contract test evidence`; `migration evidence` (проверенный путь, включая N-3 → N по §12.4); `E2E evidence`; `artifact digests`; `signature`; `status`. Статусы: `draft → candidate → certified → deprecated → revoked`. Манифест ссылается на bundle **по digest**. `revoked` bundle запрещён к новому деплою; уже развёрнутые инстансы обязаны иметь записанный путь перехода. |
| **Затронутые разделы** | §10, §14, §15, §16, §31, LAW-10 |

### AMD-10 — Observability Contract

| | |
|---|---|
| **Старый закон** | §26: health/readiness, metrics, structured logs, traces, correlation/request ID, version/build id; минимум: Platform, Component, Version, Request/Trace ID, Environment, Timestamp (+tenant_id по ADR-0009). |
| **Проблема** | Нет единого telemetry context и нет правил распространения по каналам. Не хватает `platform_id`, `component_id`, `correlation_id`, `saga_id`, `actor/service_id`. Нет правила про кардинальность `tenant_id` в метриках (быстрый способ положить monitoring). |

### AMD-11 — Data lifecycle

| | |
|---|---|
| **Старый закон** | §5 (компонент владеет данными и их жизненным циклом), §19 (состояние `retired`), §24 (аналитика), §16 (пример конфига `retention-days: 180`). |
| **Проблема** | «Владеет жизненным циклом» — не спецификация. Не определены: retention, удаление, удаление арендатора, вывод компонента из обращения, retention событий (критично для replay), retention аудита, архивирование. Пример с `retention-days` делает retention конфигурацией, а не законом. |
| **Новый закон** | Архитектурные правила (без конкретных сроков): 1. Владелец данных определяет retention, архивирование и удаление своих данных и объявляет это в контракте. 2. Удаление — **контрактно-видимое событие**, а не внутренняя операция: удаление арендатора и вывод компонента из обращения публикуют событие жизненного цикла; компоненты-потребители обязаны обработать его и не оставлять «сиротских» данных. 3. Retention событий должен покрывать окно recovery/replay; иначе replay невозможен, и AMD-05 теряет исполнимость. 4. Аудиторские записи иммутабельны и сохраняются дольше операционных данных. 5. Перевод компонента в `retired` (§19) требует до этого записанного решения о судьбе данных (экспорт / архив / удаление). 6. Конкретные сроки — конфигурация и/или политика, а не конституция (§20, §36). |
| **Затронутые разделы** | §5, §19, §24, §27, §30, LAW-03 |

## Alternatives

### A1. Ничего не менять; закрыть пробелы component-level ADR и реализацией

**Отклонено.** 20 F2-пробелов и 1 F4-противоречие затрагивают пункты, перечисленные в §35 как защищённые от изменения без ратификации (Contract model, Data ownership law, Manifest model, Golden Bundle model, Versioning law, Tenant isolation law). Component-level ADR не может создать платформенный закон: §34.1 явно разводит уровни B и D. Практическое следствие — каждый компонент реализует tenant-контекст, идемпотентность и саги по-своему, после чего унификация станет breaking change для всех (§1.4). Окно нулевой стоимости будет упущено.

### A2. Полный пересмотр конституции: ARCHITECTURE.md 2.0.0

**Отклонено.** Нарушает §40 («нельзя молча переписывать ARCHITECTURE.md») и LAW-14. Переписывание с нуля теряет ратифицированную стабильность и лишает проект точки отсчёта. Пробелы найдены в детализации существующих законов, а не в их направлении — направление верно.

### A3. Минимальные аддитивные поправки 1.1.0 → 1.2.0 через ADR-0010 — **ПРИНЯТО**

Все поправки аддитивны; ни один закон не отменяется; одна новая производная (LAW-16a); инструменты не выбираются. Объём изменений соразмерен найденным пробелам и использует окно нулевой стоимости.

### A4. Отложить всё до появления первого компонента

**Отклонено частично.** Аргумент «правила напишутся сами, когда будет код» опровергается LAW-13 в обратную сторону: такая отсрочка гарантирует появление де-факто стандартов, которые потом придётся ломать. Исключение — **K (conformance)**: конкретные линтеры и CI-проверки действительно разумно вводить по мере появления кода, поэтому AMD-12 фиксирует только сам принцип исполнимости, а инструментарий остаётся задачей реализации (уровень A).

## Consequences

### Положительные

1. **Исполнимость.** Каждый F2-пробел закрывается спецификацией, достаточной для реализации без дополнительных архитектурных решений.
2. **Автоматизируемость.** Descriptor контракта (AMD-01), идентификаторы (AMD-07), статусы манифеста (AMD-08) и состав evidence bundle (AMD-09) превращают §10/§12.4/§18/§20/§31/LAW-09/LAW-10 из prose в проверяемые условия — появляется основа для CI-гейтов (раздел «Automation Opportunities» в отчёте).
3. **Безопасность арендаторов.** AMD-02 + AMD-03 закрывают главный практический риск LAW-16 — подмену tenant-контекста вызывающей стороной; AMD-11 закрывает «сиротские» данные при удалении арендатора.
4. **Снятие противоречия.** Классификация `tenant/platform/system-scoped` даёт законный статус платформенной аналитике (§24), реестру арендаторов, каталогу и bundle registry, не ослабляя запрет доступа к данным чужого арендатора.
5. **Нулевая стоимость миграции.** Platform Instances нет; изменений в работающих системах не требуется.

### Отрицательные / риски

1. **Рост объёма конституции.** 12 поправок увеличивают ARCHITECTURE.md примерно на 15–20%. Компенсация: поправки формулируются как спецификации, которые можно вынести в приложения, оставив в §-номерах ссылки.
2. **Риск избыточной детализации (LAW-13).** Митигируется явными упрощающими клапанами: упрощённый профиль манифеста для standalone-режима (AMD-08), отказ от выбора технологий (AMD-04, AMD-10), отсутствие конкретных сроков retention (AMD-11), отказ от полного набора conformance-инструментов «на сейчас» (AMD-12).
3. **Риск ложной точности.** Часть правил (retention, retry policy) unavoidably откладывается на конфигурацию. Зафиксировано прямо: конституция задаёт правило, сроки/числа — политика.
4. **Требует дисциплины.** AMD-12 бесполезен без Conformance Matrix. Это отдельная задача реализации, не ADR.

### Нейтральное

Создание каталога `docs/adr/` — это не изменение архитектуры, а приведение репозитория к уже существующему требованию §34.
