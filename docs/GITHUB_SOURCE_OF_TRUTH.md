# GitHub Source of Truth

**Версия:** 1.0.0  
**Статус:** ACTIVE — обязательное операционное правило  
**Область действия:** ChatGPT, Arena, постоянный локальный checkout владельца, рабочие локальные checkout и GitHub.

---

## 0. Основное правило

**GitHub является Source of Truth для состояния репозитория и опубликованной истории проекта.**

Arena и Local являются временными рабочими средами и не являются самостоятельными источниками истины.

Любое состояние, которое существует только в Arena или только в Local и ещё не опубликовано в GitHub, является рабочим состоянием, а не сохранённым состоянием проекта.

Непубликованный commit не считается частью подтверждённой истории проекта до тех пор, пока он не появился в GitHub.

Пересоздание Arena-сессии или локального checkout не должно приводить к потере **сохранённого состояния проекта**, поскольку сохранённым считается состояние, уже находящееся в GitHub.

---

## 1. Что именно является источником истины

Для состояния репозитория приоритет имеет:

1. фактическое состояние GitHub, подтверждённое свежим remote-запросом;
2. локальные refs после свежего `git fetch origin` — как отражение GitHub;
3. локальные рабочие файлы и локальные commit objects — только как временная рабочая среда;
4. память Arena, ChatGPT, локального checkout, старые отчёты и предположения — только контекст, но не источник истины.

Для архитектуры и принятых решений действуют соответствующие документы проекта:

- `docs/ARCHITECTURE.md` — архитектурный закон;
- `docs/adr/` — архитектурные решения;
- `docs/OPERATING_MODEL.md` — модель ролей и полномочий;
- `docs/GIT_OPERATING_PROTOCOL.md` — операционная Git-политика;
- настоящий документ — обязательное правило Source of Truth.

Этот документ не отменяет более высокий приоритет архитектурных документов.

---

## 2. Начало каждой новой сессии

Каждая новая сессия ChatGPT, Arena или Local начинается с восстановления состояния **из GitHub**, а не из памяти предыдущей сессии.

### 2.1. ChatGPT

В начале новой рабочей сессии ChatGPT должен:

- определить актуальный `origin/main` через GitHub;
- свериться с `docs/GIT_OPERATING_PROTOCOL.md` и актуальными архитектурными документами;
- не считать старые SHA, ветки, локальные отчёты или память сессии актуальным состоянием репозитория без проверки GitHub;
- при расхождении считать GitHub источником истины для состояния репозитория;
- явно разделять подтверждённые GitHub-факты и контекст предыдущих сессий.

### 2.2. Arena

В начале каждой новой Arena-сессии до значимой работы:

```bash
git status --short --branch
git branch -vv
git log -1 --oneline --decorate
git rev-parse --is-shallow-repository
git fetch origin
git rev-parse HEAD origin/main
git rev-list --left-right --count HEAD...origin/main
```

После этого Arena должна установить:

- актуальный `origin/main`;
- текущую рабочую ветку и upstream;
- dirty/clean состояние;
- наличие локальных commit objects, которых нет в GitHub;
- необходимость восстановления или повторной реализации работы.

Если commit существует только локально и отсутствует в GitHub, Arena не должна считать его сохранённой частью истории проекта.

При невозможности подтвердить состояние GitHub Arena останавливается и сообщает ограничение.

### 2.3. Local

В начале каждой новой сессии постоянного локального checkout владельца:

```bash
git fetch origin
git switch main
git pull --ff-only origin main
git status --short --branch
git rev-parse HEAD origin/main
```

Желаемое состояние постоянного checkout:

```text
local main == origin/main
working tree == clean
```

Если локальное состояние расходится с GitHub, сначала устанавливается происхождение изменений; локальное состояние не принимается за истину автоматически.

---

## 3. Правило при пересоздании среды

Arena checkout и Local checkout могут быть пересозданы.

При пересоздании:

- GitHub не считается потерявшим историю только потому, что новый checkout shallow/grafted;
- отсутствующий в новом checkout локальный commit не считается потерянным, если он присутствует в GitHub;
- локальный commit, отсутствующий и в GitHub, и в текущем checkout, не считается сохранённым состоянием проекта;
- запрещено восстанавливать или воспроизводить такой commit «по памяти» без повторной проверки и установленного источника содержимого;
- если работа существовала только в исчезнувшей рабочей среде, она рассматривается как незапубликованная и требует безопасного восстановления/повторной реализации.

---

## 4. Publish boundary

Граница между рабочим и сохранённым состоянием проекта проходит через публикацию в GitHub.

```text
WORKING STATE
Arena / Local
      │
      │ commit
      │
      │ push
      ▼
GITHUB
      │
      ▼
SAVED PROJECT STATE
```

Локальный commit — это зафиксированное рабочее состояние Git, но до push он не является частью подтверждённой удалённой истории проекта.

После успешного push GitHub становится подтверждённым хранилищем этого состояния.

---

## 5. Поведение при расхождении

Если Arena или Local обнаруживает расхождение с GitHub:

```text
STOP
→ FETCH / CONFIRM GITHUB
→ IDENTIFY DIFFERENCE
→ DETERMINE WHETHER LOCAL STATE IS PUBLISHED
→ REPORT
→ ONLY THEN CHANGE
```

Правила:

- опубликованное состояние GitHub имеет приоритет;
- локальное состояние не подменяет GitHub;
- старый `origin/*` без свежего fetch не считается актуальным доказательством состояния GitHub;
- непубликованные локальные изменения не удаляются автоматически;
- при конфликте владельцу сообщается конкретное расхождение и требуется решение, если безопасное действие не определяется политикой.

---

## 6. Обязательная сверка в каждом новом цикле

Перед началом нового существенного этапа работы необходимо свериться с GitHub и настоящим документом.

Минимальный порядок:

```text
1. GitHub current state
2. GIT_OPERATING_PROTOCOL
3. ARCHITECTURE / relevant ADR
4. approved task / scope
5. local or Arena state
6. continue only if consistent
```

Таким образом, новая сессия не наследует состояние предыдущей сессии автоматически. Она **восстанавливает состояние из GitHub**.

---

## 7. Короткая формула

> **GitHub — Source of Truth.**  
> **Arena — disposable execution workspace.**  
> **Local — disposable working checkout.**  
> **Unpublished state — working state, not saved project state.**  
> **Every new session starts by synchronizing/verifying against GitHub.**

---

## 8. Связь с Git Operating Protocol

`docs/GIT_OPERATING_PROTOCOL.md` остаётся основным операционным протоколом Git.

Настоящий документ фиксирует его фундаментальное правило об источнике истины и обязательной синхронизации новых сессий.

Если между документами возникает противоречие, применяется установленная иерархия приоритетов, а противоречие передаётся владельцу проекта для устранения через установленный процесс.
